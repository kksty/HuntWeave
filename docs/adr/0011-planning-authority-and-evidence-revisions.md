# ADR-0011：统一计划提交、持久依赖与证据版本

日期：2026-10-09。状态：已采纳，待实施；细化 ADR-0009，P1 修订与 P2 契约分别见对应正式规格。

HuntWeave 保留四角色流程、六个 Module、PostgreSQL、LangGraph 和三个常驻服务。采用事件触发的 Run 内规划、持久任务依赖、事实与研究关系分离、显式证据绑定和版本化报告；不采用控制所有工具选择的中央 Planner、第二份自由文本待办真相、跨 Run 实时可变黑板或具有最终放行权的模型审批。

## 决定与取舍

| 决定 | 原因与代价 |
| --- | --- |
| `runs` 是研究计划的唯一提交者；harness 内规划步骤是跨任务研究判断的统一汇合点 | Collector 可按确定规则提出初始任务，Worker/Reviewer 可提交建议；Worker 保留任务内的方法与工具选择。既避免多方直接写任务造成重复，也避免把确定性动作全部交给中央模型 |
| 每 Run 同时最多一个有效规划尝试，输出可以是零项变更 | 规划读持久快照，不依赖上一轮对话。持久触发、水位、租约与版本检查承接失败恢复；需要额外的冲突与饥饿控制，但不新增 Planner 服务 |
| 事件通知用于及时唤醒，持久触发与低频补查保证恢复 | 完全取消补查会让漏通知、重启和到期等待失去恢复入口。补查不等于定时请求 LLM，不得因无事可做不断花模型预算 |
| 待办只有 ResearchTask 与依赖这一份真相；事实、任务血缘和执行图分别归属 | 多步研究靠产物与前提解锁，不能靠勾选文本或 checkpoint 推断外部成功。不引入图数据库或完整事件溯源重建体系 |
| 服务身份限定在 Project，观察保留 Run 来源；跨 Run 复用采用显式只读快照引用 | 稳定身份便于去重，但相同 IP 不证明相同部署、授权或现状。只读可以阻止改写，不能证明历史内容可信、当前有效或没有提示词注入 |
| 证据在执行时归档；Finding 与 Evidence 显式多对多绑定，结论与报告按版本提交 | 支持对照、证明、补证和反例，拒绝依域名/时间猜归属。版本冲突增加重算成本，但避免陈旧报告覆盖新增或撤回的证据 |
| 报告由 Reviewer 后的独立上下文生成步骤完成，仍属于 harness/runs/evidence | 与证据审查分开，避免写作反向决定事实；不新增常驻报告 Agent 或部署服务，模型不可用仍能导出确定性事实清单 |
| 模型风险检查仅辅助，授权和执行约束由程序决定 | 路径规则能提示部分风险，却无法判断任意脚本的全部副作用。必要检查不可用就阻断该动作；不把每个新工具变成人工审批事项 |

## 对既有决定的影响

- ADR-0009 的自主研究和持久恢复继续有效。本决定将“Collector 产生任务”精确为提出初始任务，由 `runs` 提交；不要求每个初始任务都经过 LLM。
- ADR-0010 的宿主与 IPv4/TCP 边界不变。回退必须先完成真实调用的停止/对账，再撤除管理能力；真实 Run 不切换成假执行。操作员核对不替代进程和连接回收。
- P1 保持真实执行、隔离、证据和透明控制台优先；P2 按最小闭环实现规划与报告，不提前建设完整图平台。详细行为与验收见 [P1](../specs/0002-real-execution.md) 和 [P2](../specs/0003-agent-research.md)。
