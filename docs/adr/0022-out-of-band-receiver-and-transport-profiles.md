# ADR-0022：带外接收端与新传输 profile

日期：2026-10-10。状态：已采纳，待实施。补充 [ADR-0010](./0010-real-execution-boundary-and-gate.md) 的能力边界（不就地放宽 v1 profile），并为 [ADR-0020](./0020-foothold-session-and-minimal-proof.md) 的会话提供传输面。决策依据见 [2026-10-10 双模式架构评估](../research/2026-10-10-two-mode-architecture.md)。

盲 SSRF、盲命令注入、盲 XXE、DNS 外带这一整类漏洞没有带外确认就无法判定。而现有网关只允许**既有出向连接的返回流量**（[`network_policy.py`](../../backend/src/huntweave/execution/network_policy.py)：OUTPUT 对票据端点放行 NEW/ESTABLISHED，INPUT 只接受该端口的 ESTABLISHED），反连属于 NEW 入向，会被丢弃。

## 带外接收端

新增"本次 Run 的带外接收端"为一等公民：由操作员声明地址/端口/域名与关联 token，有期限、独立网络、Run 结束即销毁。平台不拥有公网资源，也不默认使用第三方交互平台——那会把目标回带的数据送到第三方。

**必须分开两类**：带外**确认**（目标发出一次回调，属于 `coverage`）可做成**一次有界 ToolCall**（起监听 → 触发 → 等待 → 归档 transcript → 杀监听），监听随调用消亡，因此不违反"首版不支持脱离 ToolCall 生命周期的任意后台守护进程"；**反向 shell**（保持活连接）走 [ADR-0020](./0020-foothold-session-and-minimal-proof.md) 的受管会话。

必须同时定义：回调与 `Run / call / attempt` 的绑定、token 隔离与失效、迟到与重复回调、接收容量、证据归档失败、控制端失联后的处理。

两个容易写错的地方：

- **DNS 回调可能来自递归解析器，HTTP 回调可能来自代理或扫描系统**。不能要求来源 IP 等于目标 IP，也不能仅凭 token 命中确定执行主体——交互事实不等于漏洞结论。
- **"只收数据"不能禁止必要的协议响应**；禁止的是任意转发与进入控制网络。

有界窗口只能得出"**窗口内未观察到**"，不能推出"未触发"。监听资源与主动执行资源的占用**分别计量**：有界等待若持续占用执行槽，会显著压低覆盖吞吐。

## 新传输 profile

UDP/DNS（以及 IPv6、loopback TCP）**必须新增 profile 与对应验证，不能就地放宽现有规则**。需要澄清的是，**非 Web TCP 端口不是新传输能力**——目标输入已支持自定义与全 TCP 端口；缺的只是传输面。

**第二跳同样改变受信执行范围**，与接收端一并按本 ADR 的范围约束处理（见 [ADR-0021](./0021-scope-semantics-and-credential-reuse.md)）。

## 后果

- 带外不可用时，相关检查项只能记"环境阻断 / 未覆盖"，**不得记为"不存在"**，也不改变严重性、不产生 `refuted`。
- 入向监听是平台侧新开的能力面，必须走票据、限时、独立网络、只增不改的规则回读核验，并与既有出口控制一同验收。
- 容量关系（等待窗口 × 执行槽 × 覆盖吞吐）需要在实施规格中定义并纳入验收。
