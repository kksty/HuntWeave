## 1. 总体判断

现有选型适合当前单机、单组织、授权测试的阶段：隔离执行层与控制层、业务状态与图检查点分离、持久执行意图与 Runner 对账、Worker 自主研究及独立复审，都有明确职责。没有证据支持现在换框架、加图数据库、拆更多常驻服务或建立全局资产平台。

主要风险来自“规格有原则、实现仍是假链路、关键语义尚不够具体”之间的落差。优先级应是 **真实执行可信且可停止 → 根据证据决策的闭环 → 多步研究与并发 → 可信结论与版本化报告 → 用评价推动扩展**。图展示、Agent 数量和报告文案不能替代这些交付证据。

这些是针对当前约束的架构判断，不宣称存在脱离规模、成本和风险的绝对最优架构。新复杂性必须解释解决什么已观察问题、由哪个 Module 承担、如何失败恢复以及如何衡量收益。

## 3. 研究组织与持续执行

本研究撰写时系统已完成 P0-A/B：登录、授权快照、持久化 Run 与排队，P0-C/D 当时尚待交付。此处保留决策时点；当前状态见 [STATUS](../STATUS.md)。实施以当前 PROJECT 与正式规格为准。

首版需要同时满足四件事：对手动导入的 IP 发现 Web 与非 Web 服务；让 Worker 根据真实观察自主选择方法、查询资料并准备能力；在中断和多 Worker 并发下保留准确的授权、证据和执行状态；发布一次后持续自主研究到本次任务结束，而不要求操作员逐步推动。

结论是保留 `Collector → Worker × N → Reviewer → 人工复审` 和现有六个 Module，在同一个 Run 内补充**持久研究任务及依赖、按证据增量规划、按任务构建上下文、按来源记录覆盖和持续自主推进**。任务完成后停止自动执行。LangGraph 负责会话推进与检查点；业务 PostgreSQL 保存授权、任务、预算和事件；Runner 保存实际执行账本并采集原始证据。三个状态来源分别对账。

### 3.1 从发现服务到可推进的研究任务

固定扫描顺序难以表达服务之间的不同访问条件。例如同一 IP 上的 HTTP 和 Redis 需要不同的连接与验证方法；Redis 返回认证要求时，不能把 HTTP 分支一起停掉，也不能因为某个端口没有专用适配器就判定它无法研究。每个服务应先有带来源的观察，再由研究任务说明要验证什么、前提是什么、何时停止。

研究中有三种关系，职责不同：

| 关系 | 保存内容 | 关键限制 |
| --- | --- | --- |
| 服务事实 | 授权 IP、服务入口、协议/组件观察、访问条件、观测时间和证据引用 | 开放端口、指纹、漏洞实证分别表达；新发现地址不能自动进入授权范围 |
| 研究任务依赖 | 假设、任务来源、前置条件、优先级、阻断与派生任务 | 前置任务完成不等于条件成立；没有证据的计划不能升级为事实 |
| 会话执行图 | 模型决策、等待、调用、观察、复审与恢复阶段 | 不用图状态代替业务任务、预算或 Runner 账本 |

Research Frontier 是当前 Run 中待推进任务的查询结果，不另建一套调度状态机。Collector 产生初始服务任务；Worker 可以在任务内自主更换方法、搜索资料、编写脚本和解释结果。跨任务的新增、依赖或优先级变化由 harness 提出建议，runs 在短事务中校验目标范围、事实版本、依赖环、重复项和预算后提交。规划步骤不能直接执行命令、修改授权或确认漏洞。

只有关键新观察、任务完成或阻断、访问条件变化、Reviewer 补证缺口等事件才触发重新规划。相近事件合并处理；心跳、输出块和空闲轮询不反复请求模型。已有前提仍满足的任务可以按持久状态继续，局部分支受阻不冻结整个 Run。规划建议过期时重新核对事实与任务版本。任务数量、无进展次数、模型开销及 Run 总预算共同限制无效循环，不增设单服务研究时长上限。

去重以同 Run 的服务/入口、稳定研究问题和访问条件为依据；一次假设下各方法的尝试历史仍分别保留。改变标题或新建会话不能清除失败、未知结果或既有副作用。有效的新条件可以重新打开研究，不能让永久去重抹去真实变化。涉及多个服务的计划须列出全部已授权绑定，并分别通过范围检查。

### 3.2 上下文、联网研究与证据来源

每个 Worker 读取与任务相关的结构化观察、反例、已尝试方法、阻断条件和证据引用，不继承其他 Worker 的整段对话。ContextBuilder 保留当前授权与预算摘要、任务版本、活动或未知调用和恢复条件；长输出与资料正文只提供有限摘要及可回读的原文引用。摘要记录来源、版本、遗漏范围和生成时间，不能在压缩时丢掉反例或不确定性。

联网搜索和资料获取属于研究能力，必须由模型选择问题并经既定获取路径留痕。资料可以启发新假设，但网页、脚本注释和目标返回都是不可信内容，不能变成平台指令或权限。准备依赖使用洁净环境；已接触目标数据的会话不切回公网安装出口。新协议仍可由普通用户 Shell、客户端库和脚本研究，结构化包装只用于提高重复动作的稳定性。

覆盖至少区分**计划过、模型声称尝试、受信执行层记录调用、取得可用证据、独立复审**。创建任务、加载方法文档或搜索到一篇资料不能计为实际测试。ToolCall 记录只证明某次动作被执行，stdout 中的自述不能单独证明目标侧现象；关键主张要引用执行层采集的证据，必要时由 Reviewer 在独立环境复现。没有 Finding 的 Run 仍须展示未触达、已尝试、阻断和未知部分，不能显示成目标“安全”。

Reviewer 从候选主张、证据索引和反例构建新上下文，不复用 Worker 的可写环境。证据 ID 无法读取、输出不完整或复现环境不可重建时，保留候选与限制，不提升为已验证结论。机器建议与人工确认分别保存。

### 3.3 持久恢复与执行隔离

仅保存对话或研究待办，无法判断崩溃前的命令是否已影响目标。一次工具调用先在业务库持久保存唯一 call_id、预算预留、执行意图和关键事件，之后 Runner 接受并写入执行账本。恢复时按 call_id 查询账本、容器、进程和证据，再决定等待、收尾、重试或保留 unknown。结果未知且可能有副作用时不自动重复。任务计划变更也不能绕过这一核对。

目标执行仍须在隔离的普通用户会话中完成；只有受信 Runner 管理进程接触所需容器和网络管理接口。目标范围、有效期、资源、取消由工具容器外的规则落实。工具输出和研究资料不具备修改权限的能力。共享工具版本从固定来源在洁净环境重建，不复制接触过目标的可写层。

LangGraph 适合保存 AgentSession 的阶段与上下文引用，但检查点恢复可能重跑节点。业务任务、检查点和 Runner 账本因此保持不同职责，不能把任一份旧状态视为执行已完成的证明。恢复与取消的实际结果以 Runner 确认收尾为准。

### 3.4 24×7 是同一 Run 的持续自主推进

一次发布建立一个 Run，固定本次目标、授权、预算和截止时间。Collector 发现服务，Worker 在研究任务间持续作出决定；需要搜索、准备环境或等待调用结果时，保留同一 Run 的状态，并在条件满足后继续。Reviewer 可在既有预算内要求补证。权限内的这些动作不逐次请求人工确认。24×7 不要求模型或工具进程永久占用资源，而是要求系统在可运行任务存在时持续推进，并在故障后恢复原任务。

本次 Run 的执行截止默认是授权结束时间，操作员可以选更早的截止；平台不再设统一四小时上限。单次调用超时、目标出口、总预算和取消仍严格生效。授权到期、预算耗尽、服务限制、执行未知或缺少必要条件时，系统记录具体阻断和剩余工作，不创建新 Run 规避限制。其他仍可执行的分支可继续；无可执行工作时展示等待或阻断，而不无限请求模型。

正常交付顺序为 **自主渗透并留存原始证据 → AI 独立复审及有限补证 → 自动阶段结束并释放执行资源 → 人工复审**。AI 复审属于本次自主执行，证据不足时可在授权与预算内要求补充验证；人工处理的是自动阶段形成的证据与建议。单独记录自动阶段的结束时间、原因和复审完成情况，界面将“自动执行已结束，待人工复审”与“研究仍在等待条件”分开。人工长时间未处理也不保留活动执行资源，证据按保留策略留存。AI 复审不可用时明确保留未完成状态和原因，不把例外收尾伪装成完整复审。

完成条件由业务事实判定：Collector 和研究任务均已结束或有原因地终止；会影响研究的新证据和任务结果已处理，没有未决规划、待派发意图、延迟重试或补证；所有调用真实收尾，执行进程和目标连接回收得到确认，Reviewer 已完成自动复审或明确记录不可用例外。空的可领取集合只说明当前没有可调度项。结束检查与任务新增、规划应用和派发使用同一 Run 的版本约束，遇到并发新工作时重新判断，防止刚宣布完成就又发起动作。受阻任务需先明确终止及处理依赖，不能静默计为完成；未知调用继续对账。

进程重启或暂时失联后，agentd 核对原 Run 的持久任务、图检查点和 Runner 账本，先处理在途与未知调用，再接续研究。等待记录保存原因、条件、关联状态版本、重试次数、下次重试时间和截止；内存通知丢失后仍可从持久状态找回待推进工作。恢复和重复唤醒重新校验条件，不重置重试上限，不撤销用户主动暂停/取消，不重开已结束的自动阶段。事件时间线展示等待、恢复和结束依据。

这一需求下，现有模块与部署结构足以承接设计。任务依赖、按证据规划和上下文管理仍用于解决单次任务内的覆盖、协作与恢复；优化重点是把持续推进和结束条件落实为运行契约。以下情形用于检验边界，具体要求见 [PROJECT.md 第 8、12.3、14.1 节](../../PROJECT.md)：

| 情形 | 必须表现出的行为 |
| --- | --- |
| 暂时没有可领取任务，但重试尚未到期或新证据尚待规划 | 保持有原因的等待或处理状态，条件满足后自动推进；不提前宣布结束 |
| 依赖通知丢失、退避期间重启、同一唤醒重复到达 | 从持久记录恢复并幂等处理，任务、预算和重试计数保持一致 |
| 用户暂停/取消后网络恢复，或结束后迟到规划返回 | 保留用户控制与结束状态，只进行必要对账和回收，不自动启动研究 |
| AI 复审及补证完成，人工尚未处理 | 自动执行已停止，运行资源已释放，证据与复审建议可供人工查看 |
| 不断改写任务却没有新事实，随后出现真实新前提 | 无效重复不计进展；有效新条件可推动尚未结束的研究 |

单次任务结束后不周期性重新扫描。人工明确要求补证时重新校验原 Run 的授权、截止与预算并保留此前结束记录；日后明确提出的修复复测可以另建关联历史的 Run，不自动从头重跑。

### 3.5 方案比较

| 方案 | 判断 |
| --- | --- |
| 固定服务检查清单 | 易于预测，但无法根据新证据组织未知方法和跨服务前提；只适合作为有限基线对照 |
| 每个 Worker 自行维护长对话和待办 | 局部自主性强，但并发去重、任务依赖、成本与恢复难以统一核对 |
| 每步都交给一个中心规划者 | 规划可见，却增加模型调用和单点等待，也压缩 Worker 的局部方法选择 |
| 持久任务依赖 + 事件触发的 Run 内规划 | 保留 Worker 自主研究，跨任务状态由 runs 统一校验；需要实现任务版本、依赖环、去重与并发冲突检查，作为 P2 选择 |
| 单次 Run 有限授权和预算、持续推进至工作结束 | 满足一次发布后自主执行的目标；明确完成、受阻、到期和恢复条件，作为 P2 选择 |

这是一份设计判断与验收计划，尚无实测数据证明增量规划会提高漏洞发现率或持续运行的稳定性。达到各阶段验收后再作能力声明。

## 4. 执行生命周期与环境身份

有状态执行带来三组容易被混淆的等式：会话延续不等于容器未变，固定环境清单不等于运行健康，命令退出不等于资源回收完成。HuntWeave 已要求调用去重、停止确认、洁净准备和固定工具版本；本节补足这些要求之间的身份与恢复语义，采纳决定见 [ADR-0014](../adr/0014-execution-lifecycle-and-environment-identity.md)。

以下判断由现有仓库要求与执行契约推导得出，均为设计取舍，不是已经交付的保证：

| 取舍 | HuntWeave 应明确的契约 | 对应现有交付位置 |
| --- | --- | --- |
| 保留会话生命周期与单次命令的区别 | Shell 返回不等于会话资源已释放。按 `run_id/session_id/call_id` 对齐业务记录、执行账本、进程和证据；恢复前查询实际执行状态，取消后确认残留进程与连接已回收，未知副作用不重派 | [P1 规格](../specs/0002-real-execution.md) 的管理组件、取消/回收与真实动作闭环；[P2 规格](../specs/0003-agent-research.md) 的持续运行 |
| 保持环境版本与目标工作区分离 | Run 固定具体工具版本；共享制品从固定来源在洁净准备环境重建；测试工作区只属于当前会话，不能直接发布成共享工具版本。工具更新、停用和回收均需保护活动引用及必要复现制品 | P1 选择性保留；P2 洁净准备与工具发布 |
| 执行事实独立于模型判断 | 模型提出方法和预期现象，`runs` 校验并持久提交，Runner 执行并采集原始结果；模型不可自行把日志写成执行事实。受信控制、服务端鉴权、外部出口限制和取消不依赖模型在线 | PROJECT §7–12 与 P1/P2 执行契约 |
| 用实际产出验收 Agent 能力 | 同一工具集和预算下，对比正例、反例、工具失败和中断恢复。观察下一步是否随实际返回改变；任务数量、工具数量、成功退出码和演示报告均不能代替漏洞证据及独立复审 | PROJECT §14.1–14.2；P2 模型反馈与证据/复审切片 |

前三项主要强化已有边界，无需新增一套调度框架。对顶层架构最有价值的是把契约落实到一次可恢复、可停止、可追证据的完整会话，而不是增加 Agent 角色名称。

本阶段不引入的复杂性：

- 保持 `app/postgres/runner` 三个常驻服务和按需工具/准备容器；不引入集群调度、分布式文件系统、云突发容量或多种执行后端。
- 首版不改为 root Shell、不开放任意包管理提权，也不让 Agent 管理 Docker。当前普通用户、固定 helper、管理进程独占接口的要求继续生效。
- 暂停不等于任意时点内存快照；本项目的恢复仍依赖持久业务意图、图检查点和 Runner 分别对账，环境可重建不构成无条件重放的依据。
- 不把环境缓存命中率或创建吞吐量作为当前主要目标；先完成既定 P1 真实执行与隔离门槛，再按 P2 草案评审后分片实现模型闭环。

这些是 HuntWeave 当前单机规模与已确定产品边界下的判断，不把大规模集群容量设计纳入本阶段评估。后续若有本项目实际容量或隔离证据，再通过 ADR 比较成本与收益。

文档落点：本轮设计已纳入 PROJECT 0.9.3、ADR-0014、P1 规格第 3.1/3.4/3.6 节和 P2 草案第 5/5.1 节，验收分别映射回既有切片。新增的具体约束是实例身份与旧调用关联、固定环境清单和动态健康分别记录、慢工作拥塞时控制仍可推进，以及环境不可重建时的独立复审语义；已有六 Module 与三服务组织保持。架构文档交给底层开发 Agent 实施，本次不修改代码、不发布 GitHub 修改；文档规定所有权、输入输出、持久事实、失败恢复和验收，具体实现仍按切片核对真实代码。P2 草案的评审状态和真实执行的开放门槛不因本次修订改变。

## 5. 备选设计取舍

以下备选思路作为待评价方案参与比较，不作为已经验证的实现事实。

| 备选思路 | 结论 | HuntWeave 的落法与限制 |
| --- | --- | --- |
| 事件驱动 Planner、防抖、无方向时派 0 项 | 采用并补足恢复语义 | 同 Run 一次有效规划，持久触发/水位、租约/版本、最大防抖等待；漏通知由数据库补查恢复；空结果不等于研究完成 |
| 唯一意图生成器，Worker 不造意图 | 调整 | 唯一提交权归 runs；跨任务模型判断归 Run 内规划。Worker 可提出任务建议并自主选择任务内动作；确定性初始化与依赖释放不多付一次模型成本 |
| 每次规划新会话、共享 todolist | 采用结构化部分 | 新上下文从事实与未决工作构建；持久 ResearchTask/依赖就是待办，没有第二份可自由覆盖的文本计划；后继靠产物/条件解锁 |
| killWork / steerWork | 采用业务语义，不采用直通回调 | 变成暂停/取消/替代请求，经 runs 与 Runner 确认收尾；不在运行时修改既有命令或丢失证据 |
| 双图与程序去重 | 采用关系分离 | Project 内服务身份与 Run 内研究血缘分别记录，PostgreSQL 可查询和投影；不加图数据库，不扩展到根域/子域外部资产发现 |
| 前序任务活跃数据黑板与继承只读 | 部分采用 | 同 Run 相关事实视图；跨 Run 显式固定版本只读引用。实时可变继承会让恢复与报告输入漂移；只读不能防止历史错误/注入内容影响判断 |
| 删除 HTTP 方法/路径拦截与 LLM 兜底审批 | 不作为安全架构采纳；辅助信号可用 | 方法和路径不能覆盖任意脚本、非 Web 或目标实现差异；模型无最终放行权，必要检查失败阻断该动作；审批/风险检查费用如实入账 |
| 多对多流量绑定、四种用途、显式关联 | 采用并扩展 | 推广到 HTTP 与非 Web Evidence；增加 counterevidence。执行时固定证据，绑定时引用；hash 相同不抹掉不同调用的采集身份 |
| 报告 Agent 两段生成、evidence_version 乐观锁 | 采用版本契约，收窄部署成本 | Reviewer 先核验证据，独立报告上下文写作；不新增常驻服务。报告检查主张、证据、机器/人工裁定和覆盖的完整输入版本，不只检查一项 evidence_version |

## 6. 各维度约束与优先级

| 维度 | 继续保持 | 必须改善或限制 |
| --- | --- | --- |
| 产品 | 手动授权 IP，Web/非 Web，自主方法选择，自动结束后人工复审 | 不把发现数量或“全绿矩阵”当成安全保证；未覆盖、阻断、历史引用都进入交付结果 |
| 模块 | 六个 Module 与真实/测试 Adapter 共用 Interface | 当前 orchestration 集中多种职责，P2 按事务所有权逐片移出模型和证据实现；不为凑目录新建大量透传类 |
| 调度 | 单 agentd、PostgreSQL 短事务、租约、主机锁、全局预算 | 慢规划不得阻塞续租和其他 Run；跨任务串行依赖、规划冲突和结束竞争要有可执行契约 |
| 安全 | 外部出口、普通用户、洁净准备与目标隔离、固定 helper、服务端鉴权 | 就绪是动态事实；模型/规则只是辅助；只读资料仍可能污染判断；真实回退必须保留停止能力 |
| 数据 | 证据不由模型制造，原始归档和来源可核查 | 明确采集身份、多对多用途、反例、更正、历史有效性；不把 hash 当真实性或不可篡改证明 |
| 成本 | 调用前预留、复审预算保护、总额约束 | 规划、风险检查、报告、陈旧结果与失败重试都计费；零项和重复触发不造成自循环 |
| 体验 | 时间线、命令/证据、阻断、暂停/取消与恢复预览 | 先做好任务列表/依赖和证据跳转；全景图后置。恢复显示将执行什么，版本冲突不能静默重发 |
| 工具供应 | 临时/缓存/选择性保留，固定环境与来源 | P1 手动固定不能共享目标可写层；动态重建与自动发布走 P2 洁净准备，不承诺“保留就可永远复现” |
| 运维 | 单 Compose，版本/digest 固定，账本分别对账 | 数据库、检查点、执行账本、证据恢复点共同验证；空间满、保留期和活跃引用保护属于首版要求 |
| 评价 | 本地正例/反例、固定工具和同预算比较 | 多次重复测试真实反馈收益；衡量每个有效发现成本、误报、覆盖、重复动作与恢复，不靠一次演示判断优劣 |

## 7. 交付顺序与验证安排

P0-C/D 继续完成假工具闭环、持久调用、事件时间线和故障恢复，不提前创建完整研究关系。P1 先修 #9/#10/#11/#13 并完成 #15；真实链路按 #16→#18→#17，再完成 #19/#20/#21，验证 Kali 普通用户会话、出口限制、准备环境、证据归档和取消。基础并发与停止检查随执行链路前移，最后压力验收用于校准；#12 是更正后的人工确认，不属于已经关闭的任务。新增要求映射回现有切片，不新增一个庞大“架构重构”阻塞项。

P2 按正式规格的 A–E 切片：先修模型事务/身份与真实反馈，再接持久规划/依赖，随后联网与洁净准备、版本化证据/复审报告，最终验证持续运行和恢复。P2 在本地固定靶场验证：相同初始事实遇不同结果会改变任务计划；并发建议不重复入队；前置任务完成但条件未成立时后继不启动；压缩后仍能回读反例；Reviewer 不凭 Worker 自述确认；单次 Run 在跨昼夜、服务重启和有限退避后接续工作，完成后不再执行。原 P0 演示能力继续可用，未完成的 P2 不以空表/菜单对外宣传。

P3 比较覆盖收益与规划 token、等待和重复尝试成本；P4 记录长时间靶场运行的进度、恢复次数、重复动作与资源增长，优化可靠性。

后续只有出现量化证据才扩大架构：查询计划和延迟显示关系查询瓶颈时再评估图存储；单机公平调度与资源容量无法满足真实需求时再评估多机；多租户永久排除，不因多组织诉求改变；复杂身份/RBAC 只在有明确需求时再评估。更多协议优先用通用研究闭环验证收益，重复稳定且需要强约束的操作再封装。当前不新增消息中间件、向量库、Planner 服务或常驻报告 Agent。

## 8. 基础语义核实

- PostgreSQL NOTIFY 发给已监听客户端，并在事务提交后通知；我们的持久待处理标记与补查是为恢复可靠性作出的设计选择，不能把通知通道当业务任务账本。[PostgreSQL NOTIFY](https://www.postgresql.org/docs/current/sql-notify.html)
- LangGraph 中断恢复会从节点开头重新执行；因此工具副作用仍需业务幂等和 Runner 对账，独立会话不代表无须持久业务状态。[LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)
- HTTP 的安全方法定义不能保证目标实现没有副作用，RFC 还专门讨论了 URI 参数选择删除动作的情形；由此不能把 GET 或无删除关键词当成安全证明。[RFC 9110 §9.2.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.1)

以上来源只支持所述基础语义，不证明任何备选方案或 HuntWeave 已实现相应保证。实际实现须按锁定依赖版本、代码与靶场验证记录验收。
