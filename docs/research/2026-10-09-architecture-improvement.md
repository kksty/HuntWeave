# HuntWeave 架构改进研究：研究覆盖、证据与持续运行

日期：2026-10-09。状态：架构研究，单次任务持续自主执行属于 P2，长时稳定性优化属于 P3/P4。产品与安全边界以 [PROJECT.md](../../PROJECT.md) 为准；取舍记录在 [ADR-0009](../adr/0009-adaptive-research-and-continuous-execution.md)。本文讨论 HuntWeave 自身的设计问题和可验证的改进，不代表这些能力已经交付。

## 研究问题与结论

本研究撰写时系统已完成 P0-A/B：登录、授权快照、持久化 Run 与排队，P0-C/D 当时尚待交付。此处保留决策时点；当前状态见 [STATUS](../STATUS.md)，后续代码核对与细化取舍见[架构复核](./2026-10-09-architecture-review.md)。本文是历史研究依据，实施以当前 PROJECT 与正式规格为准。

首版需要同时满足四件事：对手动导入的 IP 发现 Web 与非 Web 服务；让 Worker 根据真实观察自主选择方法、查询资料并准备能力；在中断和多 Worker 并发下保留准确的授权、证据和执行状态；发布一次后持续自主研究到本次任务结束，而不要求操作员逐步推动。

结论是保留 `Collector → Worker × N → Reviewer → 人工复审` 和现有六个 Module，在同一个 Run 内补充**持久研究任务及依赖、按证据增量规划、按任务构建上下文、按来源记录覆盖和持续自主推进**。任务完成后停止自动执行。LangGraph 负责会话推进与检查点；业务 PostgreSQL 保存授权、任务、预算和事件；Runner 保存实际执行账本并采集原始证据。三个状态来源分别对账。

## 1. 从发现服务到可推进的研究任务

固定扫描顺序难以表达服务之间的不同访问条件。例如同一 IP 上的 HTTP 和 Redis 需要不同的连接与验证方法；Redis 返回认证要求时，不能把 HTTP 分支一起停掉，也不能因为某个端口没有专用适配器就判定它无法研究。每个服务应先有带来源的观察，再由研究任务说明要验证什么、前提是什么、何时停止。

研究中有三种关系，职责不同：

| 关系 | 保存内容 | 关键限制 |
| --- | --- | --- |
| 服务事实 | 授权 IP、服务入口、协议/组件观察、访问条件、观测时间和证据引用 | 开放端口、指纹、漏洞实证分别表达；新发现地址不能自动进入授权范围 |
| 研究任务依赖 | 假设、任务来源、前置条件、优先级、阻断与派生任务 | 前置任务完成不等于条件成立；没有证据的计划不能升级为事实 |
| 会话执行图 | 模型决策、等待、调用、观察、复审与恢复阶段 | 不用图状态代替业务任务、预算或 Runner 账本 |

Research Frontier 是当前 Run 中待推进任务的查询结果，不另建一套调度状态机。Collector 产生初始服务任务；Worker 可以在任务内自主更换方法、搜索资料、编写脚本和解释结果。跨任务的新增、依赖或优先级变化由 harness 提出建议，runs 在短事务中校验目标范围、事实版本、依赖环、重复项和预算后提交。规划步骤不能直接执行命令、修改授权或确认漏洞。

只有关键新观察、任务完成或阻断、访问条件变化、Reviewer 补证缺口等事件才触发重新规划。相近事件合并处理；心跳、输出块和空闲轮询不反复请求模型。已有前提仍满足的任务可以按持久状态继续，局部分支受阻不冻结整个 Run。规划建议过期时重新核对事实与任务版本。任务数量、无进展次数、模型开销及 Run 总预算共同限制无效循环，不增设单服务研究时长上限。

去重以同 Run 的服务/入口、稳定研究问题和访问条件为依据；一次假设下各方法的尝试历史仍分别保留。改变标题或新建会话不能清除失败、未知结果或既有副作用。有效的新条件可以重新打开研究，不能让永久去重抹去真实变化。涉及多个服务的计划须列出全部已授权绑定，并分别通过范围检查。

## 2. 上下文、联网研究与证据来源

每个 Worker 读取与任务相关的结构化观察、反例、已尝试方法、阻断条件和证据引用，不继承其他 Worker 的整段对话。ContextBuilder 保留当前授权与预算摘要、任务版本、活动或未知调用和恢复条件；长输出与资料正文只提供有限摘要及可回读的原文引用。摘要记录来源、版本、遗漏范围和生成时间，不能在压缩时丢掉反例或不确定性。

联网搜索和资料获取属于研究能力，必须由模型选择问题并经既定获取路径留痕。资料可以启发新假设，但网页、脚本注释和目标返回都是不可信内容，不能变成平台指令或权限。准备依赖使用洁净环境；已接触目标数据的会话不切回公网安装出口。新协议仍可由普通用户 Shell、客户端库和脚本研究，结构化包装只用于提高重复动作的稳定性。

覆盖至少区分**计划过、模型声称尝试、受信执行层记录调用、取得可用证据、独立复审**。创建任务、加载方法文档或搜索到一篇资料不能计为实际测试。ToolCall 记录只证明某次动作被执行，stdout 中的自述不能单独证明目标侧现象；关键主张要引用执行层采集的证据，必要时由 Reviewer 在独立环境复现。没有 Finding 的 Run 仍须展示未触达、已尝试、阻断和未知部分，不能显示成目标“安全”。

Reviewer 从候选主张、证据索引和反例构建新上下文，不复用 Worker 的可写环境。证据 ID 无法读取、输出不完整或复现环境不可重建时，保留候选与限制，不提升为已验证结论。机器建议与人工确认分别保存。

## 3. 持久恢复与执行隔离

仅保存对话或研究待办，无法判断崩溃前的命令是否已影响目标。一次工具调用先在业务库持久保存唯一 call_id、预算预留、执行意图和关键事件，之后 Runner 接受并写入执行账本。恢复时按 call_id 查询账本、容器、进程和证据，再决定等待、收尾、重试或保留 unknown。结果未知且可能有副作用时不自动重复。任务计划变更也不能绕过这一核对。

目标执行仍须在隔离的普通用户会话中完成；只有受信 Runner 管理进程接触所需容器和网络管理接口。目标范围、有效期、资源、取消由工具容器外的规则落实。工具输出和研究资料不具备修改权限的能力。共享工具版本从固定来源在洁净环境重建，不复制接触过目标的可写层。

LangGraph 适合保存 AgentSession 的阶段与上下文引用，但检查点恢复可能重跑节点。业务任务、检查点和 Runner 账本因此保持不同职责，不能把任一份旧状态视为执行已完成的证明。恢复与取消的实际结果以 Runner 确认收尾为准。

## 4. 24×7 是同一 Run 的持续自主推进

一次发布建立一个 Run，固定本次目标、授权、预算和截止时间。Collector 发现服务，Worker 在研究任务间持续作出决定；需要搜索、准备环境或等待调用结果时，保留同一 Run 的状态，并在条件满足后继续。Reviewer 可在既有预算内要求补证。权限内的这些动作不逐次请求人工确认。24×7 不要求模型或工具进程永久占用资源，而是要求系统在可运行任务存在时持续推进，并在故障后恢复原任务。

本次 Run 的执行截止默认是授权结束时间，操作员可以选更早的截止；平台不再设统一四小时上限。单次调用超时、目标出口、总预算和取消仍严格生效。授权到期、预算耗尽、服务限制、执行未知或缺少必要条件时，系统记录具体阻断和剩余工作，不创建新 Run 规避限制。其他仍可执行的分支可继续；无可执行工作时展示等待或阻断，而不无限请求模型。

正常交付顺序为 **自主渗透并留存原始证据 → AI 独立复审及有限补证 → 自动阶段结束并释放执行资源 → 人工复审**。AI 复审属于本次自主执行，证据不足时可在授权与预算内要求补充验证；人工处理的是自动阶段形成的证据与建议。单独记录自动阶段的结束时间、原因和复审完成情况，界面将“自动执行已结束，待人工复审”与“研究仍在等待条件”分开。人工长时间未处理也不保留活动执行资源，证据按保留策略留存。AI 复审不可用时明确保留未完成状态和原因，不把例外收尾伪装成完整复审。

完成条件由业务事实判定：Collector 和研究任务均已结束或有原因地终止；会影响研究的新证据和任务结果已处理，没有未决规划、待派发意图、延迟重试或补证；所有调用真实收尾，执行进程和目标连接回收得到确认，Reviewer 已完成自动复审或明确记录不可用例外。空的可领取集合只说明当前没有可调度项。结束检查与任务新增、规划应用和派发使用同一 Run 的版本约束，遇到并发新工作时重新判断，防止刚宣布完成就又发起动作。受阻任务需先明确终止及处理依赖，不能静默计为完成；未知调用继续对账。

进程重启或暂时失联后，agentd 核对原 Run 的持久任务、图检查点和 Runner 账本，先处理在途与未知调用，再接续研究。等待记录保存原因、条件、关联状态版本、重试次数、下次重试时间和截止；内存通知丢失后仍可从持久状态找回待推进工作。恢复和重复唤醒重新校验条件，不重置重试上限，不撤销用户主动暂停/取消，不重开已结束的自动阶段。事件时间线展示等待、恢复和结束依据。

这一需求下，现有模块与部署结构足以承接设计。任务依赖、按证据规划和上下文管理仍用于解决单次任务内的覆盖、协作与恢复；优化重点是把持续推进和结束条件落实为运行契约。以下情形用于检验边界，具体要求见 [PROJECT.md 第 8、12.3、14.1 节](../../PROJECT.md)：

| 情形 | 必须表现出的行为 |
| --- | --- |
| 暂时没有可领取任务，但重试尚未到期或新证据尚待规划 | 保持有原因的等待或处理状态，条件满足后自动推进；不提前宣布结束 |
| 依赖通知丢失、退避期间重启、同一唤醒重复到达 | 从持久记录恢复并幂等处理，任务、预算和重试计数保持一致 |
| 用户暂停/取消后网络恢复，或结束后迟到规划返回 | 保留用户控制与结束状态，只进行必要对账和回收，不自动启动研究 |
| AI 复审及补证完成，人工尚未处理 | 自动执行已停止，运行资源已释放，证据与复审建议可供人工查看 |
| 不断改写任务却没有新事实，随后出现真实新前提 | 无效重复不计进展；有效新条件可推动尚未结束的研究 |

单次任务结束后不周期性重新扫描。人工明确要求补证时重新校验原 Run 的授权、截止与预算并保留此前结束记录；日后明确提出的修复复测可以另建关联历史的 Run，不自动从头重跑。

## 5. 方案取舍与验证顺序

| 方案 | 判断 |
| --- | --- |
| 固定服务检查清单 | 易于预测，但无法根据新证据组织未知方法和跨服务前提；只适合作为有限基线对照 |
| 每个 Worker 自行维护长对话和待办 | 局部自主性强，但并发去重、任务依赖、成本与恢复难以统一核对 |
| 每步都交给一个中心规划者 | 规划可见，却增加模型调用和单点等待，也压缩 Worker 的局部方法选择 |
| 持久任务依赖 + 事件触发的 Run 内规划 | 保留 Worker 自主研究，跨任务状态由 runs 统一校验；需要实现任务版本、依赖环、去重与并发冲突检查，作为 P2 选择 |
| 单次 Run 有限授权和预算、持续推进至工作结束 | 满足一次发布后自主执行的目标；明确完成、受阻、到期和恢复条件，作为 P2 选择 |

P0-C/D 继续完成假工具闭环、持久调用、事件时间线和故障恢复，不提前创建完整研究关系。P1 验证 Kali 普通用户会话、出口限制、准备环境、证据归档和取消。P2 在本地固定靶场验证：相同初始事实遇不同结果会改变任务计划；并发建议不重复入队；前置任务完成但条件未成立时后继不启动；压缩后仍能回读反例；Reviewer 不凭 Worker 自述确认；单次 Run 在跨昼夜、服务重启和有限退避后接续工作，完成后不再执行。P3 比较覆盖收益与规划 token、等待和重复尝试成本。P4 记录长时间靶场运行的进度、恢复次数、重复动作与资源增长，优化可靠性。

这是一份设计判断与验收计划，尚无实测数据证明增量规划会提高漏洞发现率或持续运行的稳定性。达到各阶段验收后再作能力声明；当前实现状态仍以 README 和验证记录为准。
