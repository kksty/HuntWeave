# 双模式架构评估：覆盖面（coverage）与突破（breach）

日期：2026-10-10（Asia/Shanghai）。本轮修订是设计评估，不是实现，也不表示任何能力已交付。结论落点为 [ADR-0019](../adr/0019-engagement-modes-and-policy-gate.md)、[ADR-0020](../adr/0020-foothold-session-and-minimal-proof.md)、[ADR-0021](../adr/0021-scope-semantics-and-credential-reuse.md)、[ADR-0022](../adr/0022-out-of-band-receiver-and-transport-profiles.md)、[ADR-0023](../adr/0023-two-mode-visualization-projections.md) 与 [P2 覆盖面规格](../specs/0008-coverage-mode.md)。阶段状态仍只在 [STATUS](../STATUS.md) 维护。

## 1. 需求与约束

用户的实际用例决定取舍：

1. 工作中资产**特别多**，**覆盖面**是主用例：一批固定资产进去，尽量多测、挖到即停。
2. **不止 Web**：非 Web 端口与协议是当前最大缺口（现有能力只覆盖 Web/SRC 侧）。
3. **两种模式都要**：覆盖面 + 单一组织/资产的深度渗透。
4. **测绘永不接入**：任何模式下都是"操作员给一组固定资产"，平台不自行发现目标（[PROJECT §3.2](../../PROJECT.md)）。

第 4 条使 AutoHunter 式概念只能部分对齐：其"资产发现"部分不采纳，只采纳多 worker 自主研究、独立复审与情报沉淀。

## 2. 核心决定：一个内核、两个模式、三个接缝

模式差异只允许出现在三处：**动作注册表声明**、**规划器**、**停止规则**。执行内核（票据、租约、账本对账、证据、事件、出口网关、工具供给）不因模式分叉。

**初稿在此处有一个实质错误，已修正。** 初稿称"动作注册表按模式过滤 ⇒ 能力边界是代码事实"，并主张"无需改执行内核"。两处都错：

- [`shell.exec`](../../backend/src/huntweave/execution/real.py) 直接执行命令文本（`["sh","-c",command]`）。隐藏"提权""第二跳"动作**不会**让这些操作从 Shell 的表达能力里消失。[PROJECT §9.1](../../PROJECT.md) 早已写明这一限度，初稿等于拿一个反例当作保证。
- 通用执行契约本身需要扩展：UDP、入向监听、长期会话都不在现有契约内。因此正确表述是"**内核不读取模式**"，不是"内核不改"。

由此引入 **PolicyGate**：注册表只负责工具声明，规划器只提出研究建议，停止规则只管研究停止，**实际准入由 PolicyGate 决定**（动作类别、数据访问、资源限额、网络与会话能力）。需要说明的是，仓库中并不存在既有 `runs.PolicyGate`——`runs/` 下只有 `policy_version` 的使用，`contracts/capabilities.py` 的 `ReadinessGate` 是就绪门槛而非准入。**PolicyGate 是新增层**，因此 A 段不是零行为变更。

证据标准**不随模式降低**；报告可共享结构，再增加模式对应内容。模式在 Run 边界固定，agent 不得自升级。

## 3. 覆盖面（coverage）模式

目标函数是单位成本的覆盖面，停止规则是"某项主张所需的自动采证完成后停止该验证分支"。要点：

- 执行模型维持现状（一次调用一个实例，结束即撤销回收），不注册会话、提权与第二跳动作。
- 动作集增加**有界的非 Web 服务交互**（`probe_service` 形态）。需要澄清的是：**非 Web 端口不是新传输能力**——目标输入已支持自定义与全 TCP 端口；真正缺的是 UDP/DNS 这类传输面。
- 预算从"单服务限额"改为**按资产 × 服务的预算包**。代码中 `Budget` 当前挂在 Scope 上（Run 级），因此这是政策与归属调整，不是既有机制的开关。
- 工具策略偏缓存与预装；缺工具时按第 5 节阶梯处理。
- 分流与聚合是一等职能而非可选展示：确认级才进人工队列，同漏洞命中 N 台聚合为一条 Finding + N 个入口。
- KPI 为每资产成本、确认级发现率、未覆盖原因分布，不是发现数。

**挂起粒度**：挂起单位是"该资产的该检查项"，资产记为部分覆盖；同一缺口按影响面聚合为一条，不产生 N 条待办。若 1000 个资产缺同一工具，"永不整体挂起"的正确表述是"**局部缺口不阻断独立可执行分支**"；全部分支缺条件时必须明确选择等待或持久化受限结束并撤销自动唤醒——不空转，也不假称完整覆盖。

**capability_gap 的代价必须可见**：成本优先策略会持续测容易的资产，关键资产可能始终未测。因此必须保留"资产—服务—检查项"的逐项缺口明细，聚合只做展示；报告区分首次触达/部分覆盖/完全未触达；**覆盖分母注明登记依据与版本**，服务发现失败的资产不能因为没有生成检查项就消失在分母外。分母口径与 [0006 §9](../specs/0006-state-model-and-delivery.md) 的 `total_basis` 一致。

## 4. 突破（breach）模式

新增数据模型：`Identity`、`Access`、`FootholdSession`、`Loot`、`TrustEdge`。规划空间从"换 payload"变成"这个凭据还能用在哪"。

**持久会话是必需项**：没有受管会话就没有文件传输、端口转发与交互式命令。设计要点：会话属于平台不属于目标，目标侧零驻留，租约绑定 Run，全部 I/O 进证据，不允许跨 Run 存活或自启。**但初稿在这里承诺了一件做不到的事**：

- 目标进程**不受本地 Runner 的 cgroup 管理**。目标进程启动后网络中断，平台能关闭自己的连接与容器，却可能既无法终止它、也无法查询它是否退出。
- 即使最初不写盘，也不能证明目标系统没有产生日志、缓存等写入。
- 初稿同时规定"不写服务、账号"，又把新增服务、配置、账号列为遗留对象——自相矛盾。

因此改为：**平台连接状态、平台资源停止状态、目标侧进程停止证据、目标新增对象分别记录**，不用本地停止事实填充目标侧"无残留"；未知必须保留并限制后续动作。同时明确哪些是允许的最小新增、哪些是违规或意外副作用。会话与最小实证边界的完整决定见 [ADR-0020](../adr/0020-foothold-session-and-minimal-proof.md)。

**范围语义**：初稿把 [:657](../../PROJECT.md) 与 [:529](../../PROJECT.md) 的引文推论为"等于禁止横向移动"，该推论不准确——这两处表达的是不得自动扩展目标或超出操作授权。真正需要改的是**最小实证边界**与凭据获取/使用的授权语义；后者见 [ADR-0021](../adr/0021-scope-semantics-and-credential-reuse.md)。凭据复用**仍需逐目标/端口/动作校验**（与 [0007 §3](../specs/0007-research-workbench-ui.md) 的"邻域读取不授权探测"一致），校验通过后免人工批准，而不是"默认允许"。

**不可复现的验证**：初稿把 Reviewer 独立复现列为冲突，**不成立**——[0004](../specs/0004-finding-admission.md) 已允许独立复审为原始证据审阅，不要求逐项重复目标动作。正确做法是明确后渗透类主张默认走 `existing_evidence`，且不可复现不等于被反驳，也不等于证据自动充分。

## 5. 工具供给

三条判断：

1. 动态获取的真实风险不是"工具有恶意"（[ADR-0002](../adr/0002-autonomous-runtime-and-access.md) 已接受 hash 不证明无害），而是**复现性与成本**；安全边界是网络与隔离，不是白名单。但"hash 不证明无害"**不等于**风险消失：恶意或质量问题仍可能在授权目标上产生禁止的副作用。
2. **白名单是缓存，不是边界。**
3. 工具策略随模式变化：coverage 偏缓存并允许记录缺口后继续，breach 偏动态获取。

**预装扩容明确要做**：一次性镜像成本平摊所有 Run，资产多时账几乎永远算得过来。约束是"**装得宽、露得窄**"（已安装可以宽，进模型提示的清单必须小，靠可检索目录发现）；先补依赖库再补工具；预装必须跑 setuid/setcap 自检。**初稿在此处有两处事实错误**：`capstone` 是 C 实现加语言绑定、`pymssql` 依赖 FreeTDS，并非"纯 Python"；"成功率约 50%→90%"没有测量支持，已删除。预装也不存在统一体积分界——正确的比较是"更新周期内预计使用次数节省的准备成本"与"增量拉取、解包、存储、更新验证与维护成本"。

**准入分三轴**，不与"是否白名单"绑定：来源是否可固定 / 准备需要什么权限 / 成本是否超限。

| 级 | 情形 | 处理 |
| --- | --- | --- |
| L1 零获取 | 会话内已有 / 本地制品 / 离线镜像 | 会话内使用 |
| L2 受控获取 | 来源可固定 + hash 固定 + 无安装脚本 | 经受信通道送进会话，不重建会话 |
| L3 任意代码 | 含 post-install 脚本 / 需 root 系统包 / 来源不可固定 / 成本超限 | 洁净准备容器产出 toolpack |

**初稿把 L3 全部送人工是新增审批政策，已删除**：[PROJECT §6.2](../../PROJECT.md) 已允许在预授权构建 profile 内自动准备系统依赖。正确对齐是 L1/L2 与预授权构建走自主模式，"额外环境能力"按 §9.1 走授权——**来源不可固定也不会因为人工批准而变得可复现**。另需明确：洁净区准备与固定制品进入目标会话后的**使用**是两个阶段，初稿"会话内装"与"安装不在接触目标数据的工作区发生"并排书写是自相矛盾。

**执行阶梯**：缓存/预装 → 自写脚本（协议交互类优先）→ 成熟实现获取 → 重量工具（默认不做，需"轻量手段为何不够"的理由）→ 逆向类大工具（breach 默认不做，除非存在可检验的具体模式）。

**脚本闸门（修正）**：初稿的"一个已知负例"**不构成闸门**——永远返回"否"的脚本能通过任何负例却漏掉全部正例；脚本与负例若由同一模型生成还可能共享同一错误假设。正确闸门至少三段：解析与异常处理检查、**具有已知结果的正反例**、实际主张要求的因果对照。超时、认证失败、畸形响应必须返回未知或失败，不能返回"否"。**缺负例不禁止脚本收集原始观察，但不允许其未经验证的判定充当确认依据**（与 [0005](../specs/0005-capability-claim-criteria.md) 的对照规则一致）。脚本通过自检也不自动获得共享发布资格。

## 6. 带外确认与不确定结论

**带外必须切开两类**：带外**确认**（目标发出一次回调，属于 coverage，可做成一次有界调用）与**反向 shell**（目标连回并保持活连接，属于 breach，必须是受管会话）。有界调用内的监听随调用消亡，不违反"不支持脱离 ToolCall 生命周期的后台守护进程"。

**不需要公网**：靶场内网与 VPN 场景下监听端就在工具容器或跳板机；只有"目标在公网、平台在 NAT 后"才需要中继或纯 DNS 外带；目标完全无出向时无 OOB 可用。平台把 OOB 端点做成操作员声明，不拥有公网资源，避免第三方交互平台把目标数据送出。

**关键修正**：初稿称"入向监听是唯一的新网络能力"**不准确**——第二跳同样改变受信执行范围（本地 Runner 校验第一跳，不能证明目标主机发出的第二跳受网关约束）。两者与新传输 profile 一并由 [ADR-0022](../adr/0022-out-of-band-receiver-and-transport-profiles.md) 处理。另需明确回调与 `Run/call/attempt` 的绑定、token 隔离与失效、迟到/重复回调、接收容量、归档失败、控制端失联；DNS 回调可能来自递归解析器、HTTP 回调可能来自代理或扫描系统，不能要求来源 IP 等于目标 IP，也不能仅凭 token 命中确定执行主体；"只收数据"不能禁止必要的协议响应，禁止的是任意转发与进入控制网络；有界窗口只能得出"窗口内未观察到"；监听资源与主动执行资源的占用必须分别定义，否则会显著压低覆盖吞吐。

**不确定结论**：先分失败原因——环境阻断（记未覆盖原因）、方法不适用、动作已执行但无可观测响应（未知）。初稿的四条准入**不足**：

- 客户端请求完成、退出码为零不证明目标上的漏洞触发成功。
- 没有响应不能单独区分出口受阻、未触发与观察失败。
- "带外命中直接确认"过强：DNS 交互可能是正常功能、WAF 或第三方扫描器产生的（[PortSwigger 对交互事实与漏洞结论的区分](https://portswigger.net/kb/issues/00300200_external-service-interaction-dns)）。
- CVE/公告适合作为已知漏洞线索的要求，不应成为所有未知方法获得支持结论的必要条件。

因此 `suspected_blind` 降为**原因或证据标签**，映射到既有 `supported/undetermined`，不另造竞争状态；缺 OOB 改变证据充分性，不直接改变严重性，更不产生 `refuted`。弱证据按类型分开表达（时间差分须重复取统计、错误/状态差分、副作用可观测、带外命中），承载于既有三层契约与前提门。

## 7. 停止、求助与脱困

**初稿的"有没有新假设"判据已废弃**：它可由模型改写假设绕过，也会把必要的对照、统计重复与独立复现误判为打圈。既有 [PROJECT §8.5](../../PROJECT.md) 的进展定义更准确——新增有效观察、假设得到支持或反驳、访问前提变化、覆盖缺口减少；改写标题、重复搜索与重复自述不计进展。检测粒度落在研究问题或分支，某分支打圈不停掉该资产的其他检查。

**成本不作为模型的主观权衡**，而作为事实暴露（剩余预算、该资产消耗、覆盖进度、已尝试次数）；不让模型估 token 成本。介入由可观测量触发：打圈→脱困；条件缺失→直接记缺口；越界→生成具体请求并阻塞该检查项；L3 环境能力→聚合进人队列不阻塞；成本失控→停该资产并记账。绝大多数"需要人"的场景应产出请求后继续，只有越界动作真正阻塞。

**脱困 agent 保持，但必须可证伪**：固定靶场 + 同一触发条件 + 三组对照（立即结束 / 原规划器继续 / 独立上下文脱困）+ 相同总预算，统计脱困调用及其后续全部成本；主指标是增量有效覆盖、有效证据、误报/误阻断与端到端成本，"生成了新假设"只算中间产物。若收益仅来自多花一轮预算，独立 agent 未证明价值。同一缺口影响大量资产时先聚合诊断。按 [0003 §8](../specs/0003-agent-research.md) 的口径，规划收益不足先减触发和职责，不以增加 Agent 数量作为改进；因此它先作为规划器的受限策略实现，不新增长期角色。

## 8. 可视化横切面（初稿遗漏）

初稿完全没有覆盖可视化层，这是缺口而非删除。现有设计比初稿完整，本轮不重新设计，只补模式带来的新增：

- **既有基线不变**：[PROJECT §12.1](../../PROJECT.md) 的七个可观察视图、[ADR-0015](../adr/0015-graph-semantics-and-projection-boundary.md) 的只读投影与水位语义、[0007](../specs/0007-research-workbench-ui.md) 的工作台骨架与状态视觉编码表。
- **coverage 需要新增投影**：0007 的"服务组/分支泳道"是为单 Run 少量服务设计的，几千资产 × 几十检查项会不可读。coverage 的问题是"还有什么没测、为什么没测"，需要**覆盖矩阵 + 缺口分布**视图。0007 状态栏的"未覆盖 N / 受阻 N"两个计数不足以表达"缺能力"这类缺口。
- **breach 需要第三类投影**：`Identity / Access / FootholdSession / TrustEdge` 不属于既有的服务事实关系与研究血缘关系两类。按 [ADR-0015](../adr/0015-graph-semantics-and-projection-boundary.md)"不新建第二份研究状态"的原则，应增加第三个投影视角，而不是新图或新库。
- **初稿重复发明了两处**：聚合下钻与覆盖分母口径在 0007 与 0006 已有规定，改为引用。

决定见 [ADR-0023](../adr/0023-two-mode-visualization-projections.md)。

| 预算粒度 | **初稿过宽**：`Service` 本就绑定主机；"单服务"与"资产×服务"未必是不同粒度，且代码预算仍是 Run 级 |
| 不可复现验证 | **初稿错**：不存在所述冲突，0004 已允许审阅既有证据 |
| 导入上限 | 成立；CIDR 展开预览属输入边界，跨 Run 资产台账还涉及身份、时效与历史事实 |
| 动态安装 | 阶段描述准确，但分级准入不消除准备、清单、恢复与发布路径的实施工作 |
| L3 转人工 | **初稿错**：§6.2 已允许预授权构建自动准备，全部转人工是新增审批政策 |
| 能力边界 | **初稿错**：注册表与出口网关无法约束通用 Shell 在已授权服务上的全部操作语义，原文已明确说明该限度 |

另有三处初稿事实错误已在第 5、8 节与 §15（开源）修正：依赖库的原生实现、编造的成功率数字、许可证与镜像发布的现状描述。

## 10. 未决与开放问题

1. **打圈与探索的判据**：采用既有进展定义后，是否仍会把深度探索误判为重复，需要实施规格固定阈值并在验收中验证。
2. **脱困 agent 的收益计量**：若无法在对照实验中证明增量有效覆盖，按 0003 口径应删除该能力。
3. **coverage 的"确认即停"与确认等级的循环依赖**：需明确"证据要求已满足、待确认等级完成"与 `confirmed` 的区别，否则服务端执行主张会卡死。
4. **OOB 的容量占用**：有界等待窗口与四个执行槽的关系未定，可能显著压低覆盖吞吐。
5. **预装扩容的边界**：镜像多大时"装得宽"开始伤害冷启动与自身攻击面，需要冷/暖缓存的分别测量。
6. **规模化上限**：`agentd` 顺序推进、账本全量序列化、事件游标行锁三处是**待测瓶颈**而非已测上限，需要压测后再决定是否调整部署结构。
7. **Project 结构的单点**：PROJECT 为单文件长篇且被大量反向引用，拆分是可选的整理项，不与本决定绑定。

## 11. 覆盖面模式的目标类与复测语义

本节是 2026-10-10 之后按用户在实际使用中的观察补充的，落点为[覆盖面规格 §3.7、§5.1](../specs/0008-coverage-mode.md)。

### 11.1 「广度优先 / 深度优先」类比的三处失效

两种模式**方向上**对应带深度上限的广度优先与深度优先，但不能只用 DFS/BFS 表述：

1. **图不是给定的，而是边走边建。** BFS 的完备性保证依赖分支因子已知、图可枚举；这里的节点（服务、端点、凭据、可达主机）由探索行为本身产生。因此覆盖面**永远不能声称完备**。
2. **边权不均匀。** 图搜索每条边代价为 1；这里一个节点可能需要一套工具链，比另一个贵几个数量级。真正的调度是"按单位成本期望收益优先 + 深度上限"，不是队列顺序。
3. **目标函数不同，而非遍历顺序不同。** BFS 与 DFS 是同一目标的两种顺序；覆盖面最大化集合上的确认覆盖，突破最大化单个目标上的访问权。**这才是模式必须是策略维度而不是规划器参数的原因。**

另有一个 BFS/DFS 完全没有的维度：**是否积累状态**。覆盖面每个目标独立、无状态；突破积累身份与访问。

因此固定表述为「**覆盖面＝无状态广度；突破＝有状态深度**」，不用"广度优先 / 深度优先"作为定义。

### 11.2 检查类成熟度分级

用户观察到 API 未授权类产出集中。原因是这类检查**判定为布尔值、有明确对照、无需带外、无需链条**，且一次写好规则可批量套用于同类资产——正是覆盖面模式性价比最高的一类。

风险随之而来：**未授权类多，部分原因是它最容易测，不是它最有价值。** 若 KPI 只看总发现数，产出会被易测类主导而无法识别"只在易测类上有覆盖"。因此按可判定成熟度分级（可判定类 / 需带外类 / 需链条类），并**按检查类分别报告命中率与覆盖率**。

### 11.3 深挖额度

用户使用的平台为每个目标设置有限"深挖次数"，用尽即转下一个，速度与预算因此有保障——**这是用硬上限换来的，不是靠模型自律**。落点：深挖额度是每资产（或每发现）的有限再尝试次数，且**只能把"可疑"推进到"确认"，不能把"确认"推进到"利用"**；后者属突破模式。额度用尽不改变覆盖状态。

### 11.4 复测语义：为什么"打回复测反而测不出来了"

用户观察到的现象——复测后原先测出的不复现——**通常不是漏洞消失，而是第一次的判定不可靠**。五种成因：

| 成因 | 表现 | 处置 |
| --- | --- | --- |
| 判定没有对照（只看状态码或关键字） | 第一次命中是误报，复测"不命中"其实是对的 | 强制差分对照 |
| 第一次留下副作用（建号、改配、触发限流或锁定） | 复测环境已不同 | 先核对未记账副作用；有脏数据则复测不可比 |
| 目标侧易变（修复、灰度、CDN/WAF 策略、动态内容） | 时好时坏 | 固定可比对的最小证据片段，比对"是否仍满足原判定条件" |
| 凭据或时间窗失效、出口被过滤 | 请求被拒 | 属条件缺失，不是不成立 |
| 复测前置条件不同（换账号、换路径、换 header） | 不可比 | 复用原调用参数、条件与环境身份，并记录差异 |

四条结论：

1. 复测是**有界再验证**，不是重跑。
2. 条件不再满足时标「待补证（缺条件）」。
3. **"第一次成立、复测不成立"不产生 `refuted`**，正确结论是未决。这是 [0005 §3](../specs/0005-capability-claim-criteria.md)"缺条件不产生 refuted"最容易被违反的具体场景。
4. 判定必须有差分对照；提高可判定性比提高复测次数有效。
