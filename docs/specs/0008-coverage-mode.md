# P2：覆盖面模式与覆盖能力

状态：设计已确定，待实施。本规格是 `coverage` 测试模式的行为、失败与验收来源；模式、准入与边界见 [ADR-0019](../adr/0019-engagement-modes-and-policy-gate.md)、[ADR-0022](../adr/0022-out-of-band-receiver-and-transport-profiles.md)、[ADR-0023](../adr/0023-two-mode-visualization-projections.md)，评估依据见[双模式架构评估](../research/2026-10-10-two-mode-architecture.md)。突破（breach）模式不在本规格范围内。

## 1. 目标与职责

对一批**操作员声明的固定资产**尽量多测：目标函数是单位成本的覆盖面，不是单个目标的深度。本规格负责服务发现与识别、有界非 Web 服务交互、带外确认、能力缺口记账、分流与聚合、停止规则。**不负责**持久会话、提权、横向移动与第二跳——这些对象在覆盖面模式下**不注册也不读取**。

覆盖面模式不接入外部资产测绘；资产永远由操作员声明（[PROJECT §3.2](../../PROJECT.md)）。

## 2. 模式与准入契约

| 项 | 要求 |
| --- | --- |
| 模式字段 | Run 固定 `engagement_mode`，随 `EXECUTION_POLICY_VERSION` 进入授权快照；旧 Run 不被当前构建改写 |
| 与执行模式并存 | `engagement_mode` 与既有 `mode = demonstration / real` 是**互相独立的两个字段**，不复用也不替换 |
| 准入 | 由 PolicyGate 把模式与当前授权解析为不可变有效策略（动作类别、数据访问、资源限额、网络与会话能力）；动作注册表只声明工具，规划器只提出研究建议，都不构成准入 |
| 执行内核 | **不读取模式**；但可为能力扩展（传输面、带外接收端） |
| 证据标准 | **不随模式降低**，与突破模式使用同一套主张契约与确认等级 |
| 模式切换 | 只在 Run 边界；agent 不得自升级；覆盖面产出的候选由操作员开新的突破 Run |

### 2.1 可表达不等于可执行

**契约字段能构造、能持久化、能查询，不等于该 Run 能执行。** 两者是不同层次的判断，验收也必须分开，不能因为新增了 `engagement_mode` 就放宽执行门槛（[ADR-0026](../adr/0026-contract-alignment-readiness-cidr-and-queue.md)）。

| 层 | 判断 | 本轮的要求 |
| --- | --- | --- |
| L1 语法层 | `engagement_mode × mode = demonstration / real` 的四种组合**可表达** | 字段加入后四种组合的取值合法、组合可表达，拒绝或就绪语义**可区分**（[#25](https://github.com/kksty/HuntWeave/issues/25) 验收 2 只覆盖本层）。本层**不承诺四种组合当前都能创建 Run**——`mode=real` 的两组在 L2 于创建阶段即被拒绝 |
| L2 部署就绪层 | [ADR-0010](../adr/0010-real-execution-boundary-and-gate.md) 的四项门槛**同时**成立才允许 `real_execution_ready=true` | **不放宽**。请求真实执行的 Run 在门槛未逐项满足时被拒绝（现在四条不同时满足，`mode=real` 在创建阶段即得 409 `real_execution_not_ready`） |
| L3 授权绑定层 | Run 的 `execution_profile` 必须与其授权快照一致；快照在提交时写入 `policy_version`，后续构建不得改写 | **不放宽**。旧授权快照的 Run 在升级后保持原策略与结论语义 |
| L4 模式准入层 | `breach` 注册表**先为空**；空注册表不得被解释为「研究完成」 | **不放宽**。空注册表产生「模式未就绪/无可用动作」，不产生完成结论 |

**L1 与 L2 是不同字段对，不得混用**：#25 的四种组合是 `engagement_mode × mode`；代码里现在存在的是 `mode × execution_profile`。后者中 `execution_profile != "fake-p0-v1"` 的两组在创建阶段就被 `runs/service.py:107-108` 拒绝，因此「可表达」既不能推出「能创建 Run」，更不能推出「能执行」。把「可表达」读成「可执行」是本规格与 [#25](https://github.com/kksty/HuntWeave/issues/25) 之间唯一需要消除的歧义，其余结论不变。

## 3. 行为

### 3.1 发现与传输面

对导入 IP 做范围内端口发现与服务识别，事实归档；不把裸 IP 等同于 `http://IP:80`。**非 Web TCP 端口不是新传输能力**——目标输入已支持自定义与全 TCP 端口。UDP、DNS（以及 IPv6、loopback TCP）**必须新增 profile 与对应验证，不能就地放宽现有规则**。

### 3.2 有界服务交互（`probe_service`）

输入：`service_id`、可选凭据引用、超时。输出：连接/认证/协议事实与证据 ID。要求：

- 认证状态允许 `unknown`；**连接成功不得标为漏洞成立**。
- 参数与目标绑定由票据承载，不接受请求中指定任意目标。
- 属于"反复出现、需要稳定解析"的能力，按 [PROJECT §10.1](../../PROJECT.md) 添加结构化包装；协议适配器仍不是前提，没有包装不构成"不支持测试"。

### 3.3 带外确认

带外**确认**做成**一次有界调用**：起监听（绑定端口 + 关联 token）→ 触发 → 等待（有上限）→ 归档 transcript → 杀监听。监听随调用消亡，因此不违反"不支持脱离 ToolCall 生命周期的后台守护进程"。保持活连接的反向 shell 属突破模式，不在本规格。

必须满足：回调与 `Run / call / attempt` 绑定；token 隔离与失效；迟到与重复回调有明确处置；接收容量有界；归档失败阻断受影响执行；控制端失联后按既有停止语义收尾。**不能要求回调来源 IP 等于目标 IP**（DNS 可能来自递归解析器、HTTP 可能来自代理或扫描系统），也不能仅凭 token 命中确定执行主体。"只收数据"不禁止必要的协议响应，禁止的是任意转发与进入控制网络。有界窗口只能得出"**窗口内未观察到**"。

带外不可用时，相关检查项记**环境阻断**，不改严重性，不产生 `refuted`。

### 3.4 能力缺口与挂起粒度

- 挂起单位是"**该资产的该检查项**"，不是整个资产。资产在部分检查项因缺口未执行时记为**部分覆盖**。
- 缺口按影响面**聚合**：同一次缺口影响 N 个资产、M 个检查项时只产生一条待办，同时保留「资产—服务—检查项」逐项明细。
- **局部缺口不阻断独立可执行分支**；全部分支都缺条件时必须明确选择等待或持久化受限结束并撤销自动唤醒。不得空转，也不得假称覆盖完整。
- 覆盖分母注明登记依据与版本，沿用 `total_basis = exact / estimate / unknown`；分母未知不显示覆盖百分比。**服务发现失败的资产不能因为没有生成检查项就从分母消失。**

### 3.5 分流与聚合

命中级 → 可疑级 → **确认级才进「确认复核」队列**。同一漏洞在 N 个资产命中时聚合为**一条 Finding + N 个受影响入口**。聚合是视图：**每个入口保留独立证据、条件与判定，不能用一台的实证确认其余入口**。

「确认级才进人工队列」说的是**确认复核**这一个队列目的，不是「人工／复核队列只有确认级能进」。缺证据、分类争议（即 §3.5.2 的 `classification` 目的）与失效重评同样入队，**但注明目的**（[0006 §3.2](./0006-state-model-and-delivery.md)、[#28](https://github.com/kksty/HuntWeave/issues/28) 范围 4）。两者必须同时成立，否则「待补证（缺条件）」这类结论无处登记。

#### 3.5.1 确认级、证据满足与 `confirmed` 三分

| 概念 | 属于 | 含义 |
| --- | --- | --- |
| 证据要求已满足 | 谓词（对固定契约与输入版本计算） | 该主张的展开后有效要求齐备；**不是** A1 状态 |
| 确认级就绪 | 分流候选状态 | 可以进入「确认复核」队列；`required_confirmation_level` 尚未完成 |
| `confirmed` | A1 主张判定 | 达到契约确认等级、必要输入当前有效 |

自动采证**不等待人工**：某项主张所需的自动采证完成后，由 `StopPolicy` 停止该验证分支并进入独立复审（§3.6），其他检查继续。服务端执行能力默认 `human` 等级（[0006 §3.1](./0006-state-model-and-delivery.md)），因此**把「确认级」直接映射成 `confirmed`、或把「等人工确认」实现成「不能继续采证」，都会让覆盖面模式死锁**。队列是待处理工作的登记处，不是执行流水线的闸门。

#### 3.5.2 队列目的

各目的有独立入口条件与退出路径，**任一目的不得阻塞其他目的**：

| 队列目的 | 入口条件 | 允许的复核动作 | 退出路径 | 不得变成 |
| --- | --- | --- | --- | --- |
| `confirm` 确认复核 | 证据要求已满足且达确认级 | 确认、退回 | 裁定 `confirmed`，或回到 `supported` 并列缺口 | 权限内执行前的逐次审批 |
| `evidence_gap` 缺证 | `satisfied=false` 且已登记要补哪条证据 | 要求补证、放弃该分支 | 补证完成，或持久化带原因的未决结束 | 因 `satisfied=false` 丢掉重审需求 |
| `classification` 分类澄清 | 分类存在争议 | 澄清分类与适用判据 | 契约明确后重评，或保留未决 | 冻结独立的合法研究 |
| `lapsed_retest` 失效重审 | 必要输入失效、结论 `lapsed` | 登记并决定是否重做 | 用户明确请求后重评；**不自动花费预算或重开目标测试** | 自动恢复执行 |
| `retest` 打回复测 | 已登记「要补哪条证据」 | 有界再验证 | 复用原参数、条件与环境身份并记录差异（§5.1） | 重跑整个资产 |

队列不静默丢弃；等待人工不占目标执行槽，也不阻止独立研究或自动阶段收尾（[0006 §3.2](./0006-state-model-and-delivery.md)、[PROJECT §12.3](../../PROJECT.md)）。超 SLA 只能提醒或升级，**不能自动 `confirmed`**。

### 3.6 停止规则

**某项主张所需的自动采证完成后，停止该验证分支并进入独立复审；其他检查继续。** 停止由 `StopPolicy` 保证，不交给模型判断。

必须区分"证据要求已满足、待确认等级完成"与 `confirmed`：服务端执行能力默认最终人工确认（[0006 §3.1](./0006-state-model-and-delivery.md)），若把"确认级"直接映射成 `confirmed`，服务端执行主张会卡死。三者的归属见 §3.5.1，队列目的与不得死锁的约束见 §3.5.2。**停止的是已经完成自动采证的那条验证分支，不是整个 Run，也不是「等人工」的登记工作。**

### 3.7 检查类分级与深挖额度

**检查类按可判定成熟度分级**，覆盖面优先执行可判定的一类。这不表示其他类不重要，只表示在"单位成本覆盖"的目标函数下它们的性价比不同：

| 级别 | 特征 | 例子 | 覆盖面处理 |
| --- | --- | --- | --- |
| 可判定类 | 判定为布尔值、**有明确对照**、无需带外、无需链条 | 未授权访问、越权、敏感信息暴露、开放服务 | 优先；可批量套用于同类资产 |
| 需带外类 | 需要目标发出可观察的回调 | 盲 SSRF、盲注入、盲 XXE | 有带外接收端时执行，否则记环境阻断 |
| 需链条类 | 需要跨步骤的状态积累 | 提权、横向移动、组合利用 | 覆盖面不做；记能力缺口或转突破模式 |

**按检查类分别报告命中率与覆盖率**，不只用总发现数。总发现数会被易测类主导：某类产出集中，可能只是因为它最容易测，而不是因为它最重要。没有分类统计就无法识别"只在易测类上有覆盖"。

**深挖额度**：单个资产（或单个发现）上允许的有限再尝试次数，用尽即转向其他工作。两条硬边界：

1. **深挖只能把"可疑"推进到"确认"，不能把"确认"推进到"利用"**；后者属于突破模式，覆盖面模式下不注册相应动作。
2. 额度计入该资产预算；**用尽不改变覆盖状态**——仍记部分覆盖与原因，不因"深挖过了"就记为已覆盖。

模型不能通过申请更多深挖来延长一个已经确认的分支；停止规则与深挖额度共同保证"确认即停"。

## 4. 证据与不确定结论

先分开失败原因：

| 情况 | 结论 |
| --- | --- |
| 无出向 / 无路由 / 出向被过滤 / 无带外条件 | `environment_blocked`，记未覆盖原因 |
| 版本、认证或前置不满足 | 方法不适用 |
| 动作确已执行但无可观测响应 | **未知** |

`suspected_blind` 是**原因或证据标签**，映射到既有 `supported / undetermined`，**不新增竞争状态**。下列情形不足以判定：

- 客户端请求完成、退出码为零，不证明目标上的漏洞触发成功。
- 没有响应不能单独区分出口受阻、未触发与观察失败。
- 带外命中是交互事实，可能是正常功能、WAF 或第三方扫描器产生，不自动等于漏洞结论。
- CVE/公告适合作为已知漏洞线索的要求，**不是所有未知方法获得支持结论的必要条件**。

弱证据按类型分别表达且不可互相顶替：时间差分（须重复取统计，单次不算）、错误/状态差分、副作用可观测、带外命中。承载于既有主张契约、能力类判据与前提门三值状态。

**未知是一等结论**：报告写"未确认（原因：本次运行无带外条件）"，不强行判定，也不把缺条件写成"不存在"。

## 5. 失败、恢复与对账

- 沿用既有 `ToolCall` 状态与停止确认语义；带外监听的启动失败、归档失败与取消分别记原因，不合并成一个"失败"。
- 缺口与覆盖记录不影响调用对账；结果未知的调用仍先核对再决定，不盲目重试。
- 模式字段加入后，旧 Run 保持原策略版本与其结论语义。

### 5.1 再验证（复测）语义

复测**不是重跑，而是有界再验证**：复用原调用的参数、条件与环境身份，并**记录与上次的差异**。差异本身就是结论的一部分。

- 条件不再满足时（凭据过期、时间窗失效、出口被过滤），标 **「待补证（缺条件）」**，不是「不成立」。
- **"第一次成立、复测不成立"不产生 `refuted`**：正确结论是未决——条件已变，当前无法重现。这与 [0005](./0005-capability-claim-criteria.md)"目标不可达、工具超时、畸形输出或缺条件不产生 refuted"一致；复测失败是最容易违反它的具体场景。
- **副作用未核对的调用不得作为复测基线**：先走既有对账。上一次测试若留下了未记账的写入（新建账号、修改配置、触发限流或锁定），复测的环境已经不同，结果不可比。
- **判定必须带差分对照**（带条件与不带条件的可比对）。没有对照的命中在复测时不稳定是必然的，不是目标发生了变化。
- **但「是否要求对照」本身按主张类型适用，不由本节一律强制。** 适用与不适用的通则见 [0005 §6](./0005-capability-claim-criteria.md)：对照**可以**由同一次采集中的既有观察满足；**不得为满足形式而追加目标动作**；声明的「不适用」必须符合该主张类型的适用条件，由复审确认并留下记录与依据，**程序校验其类别、引用与版本是否齐备，模型不能单方豁免**。本节的差分对照是「复测必须可比」的充分条件说明，不是独立于判据表的全局强制项。

实践中"复测反而测不出来了"通常不是漏洞消失，而是第一次的判定不可靠。提高可判定性比提高复测次数有效。

## 6. CIDR 批量导入：边界变更提案与待确认项（**未决，现状不变**）

[#30](https://github.com/kksty/HuntWeave/issues/30) 与本节 C-F 行的验收文字要求「接受 CIDR，但只做展开、由操作员确认展开结果」。**这条验收标准当前不成立**，因为它与 [PROJECT §3.2](../../PROJECT.md)「域名、URL、CIDR、ASN 作为批量目标来源 …首版 IP 输入接口明确拒绝」及 [PROJECT §4.2](../../PROJECT.md)「首版不接受混入端口、协议、域名、网段或任意命令的行」直接冲突。已核验的现状是：后端 `runs/inputs.py` 对整行做 `ipaddress.ip_address` 解析，任何含 `/` 的行落到 `invalid_ip`；前后端都没有 CIDR 或地址折叠分支；`TARGET_LIMIT = 100` 按去重后的规范化目标计数（证据见验证记录 `0020`）。

**当前生效的规则（在明确范围决定之前不变）**：

1. 批量目标来源只有操作员的 IP 清单；CIDR/域名/URL/ASN 在输入接口被拒绝，原因码为 `invalid_ip`，逐行反馈。
2. 单 Run 上限 `TARGET_LIMIT = 100`；**不存在任何绕过该上限的路径**。
3. 平台**不自动扩大目标集合**：重定向、证书、响应体与页面链接中出现的新域名或 IP 只作为线索（[PROJECT §4.2](../../PROJECT.md)）。
4. IPv6 保留自己的原因码 `ipv6_environment_unsupported`，与 CIDR 的拒绝原因不混。

**具体边界变更提案（待确认后才可成为规则）**：

| 项 | 提案 |
| --- | --- |
| 接受形式 | 仅接受**单个 IPv4 CIDR 前缀**（单个地址的 `/32` 等价于现有 IP 行）；一行一个前缀，不混入域名、端口、协议或命令 |
| 展开语义 | 平台只做**确定性展开**，结果在提交前可见、可逐行删除或补充；**操作员确认展开结果后才创建 Run**，未确认时不创建 |
| 扩大目标的红线 | 展开**不得**由历史台账、证书、重定向或任何线索触发；不得从已有目标推导出未声明的网段（[PROJECT §3.2](../../PROJECT.md)、[0003 §4](./0003-agent-research.md)） |
| 上限口径 | 展开**后**的规范化不同 IP 数仍受 `TARGET_LIMIT` 约束；超限时按行给出原因（`target_limit_exceeded`），不静默截断 |
| 受保护地址 | 展开结果逐个过现有保护清单（环回、链路本地、未指定、组播 → `protected_address`），保护地址不因来自 CIDR 而放行 |
| IPv6 | 提案**不含** IPv6 CIDR：仍按 `ipv6_environment_unsupported` 拒绝，除非同批解决出口隔离 profile（[ADR-0010](../adr/0010-real-execution-boundary-and-gate.md)） |
| 跨 Run 台账 | 展开结果不写入可复用的跨 Run 资产台账；台账只提供只读引用，**不默认继承凭据、当前访问能力或本轮覆盖结论** |

**若提案被接受，必须同时修订的位置**：

- [PROJECT §3.2](../../PROJECT.md) 的排除表行「域名、URL、CIDR、ASN 作为批量目标来源」（改为「域名、URL、ASN」并加注 IPv4 CIDR 的展开条件），以及 §4.2 的首条输入语义。
- [PROJECT §12](../../PROJECT.md) 的「单 Run 导入上限」行：注明上限在 CIDR 展开**后**计算。
- §8 实施切片表的 C-F 行与 §7 验收标准（新增展开预览、逐行反馈、超限原因三条）。
- [#30](https://github.com/kksty/HuntWeave/issues/30) 正文的范围 2 与验收 2、3（由协调人在 Issue 上执行，见验证记录 `0020` 的更正建议）。

**待确认项（需操作员 / 产品决定，未确认前按现状实现）**：

1. **是否纳入范围**：首版是否接受 CIDR 作为批量目标来源，还是继续按 [PROJECT §3.2](../../PROJECT.md) 拒绝、把 CIDR 留作独立需求？
2. **上限如何表达**：`TARGET_LIMIT = 100` 保持现值，还是随 CIDR 支持同步提高？若提高，预览路径与容量影响如何一并说明（[#30 范围 1](https://github.com/kksty/HuntWeave/issues/30) 要求不允许只在提交路径放宽）？
3. **是否接受非 `/32` 的整段前缀**：接受的最小/最大前缀长度是多少；是否要求操作员显式确认「本次授权覆盖整段」？
4. **保护地址与私有网段的处理**：整段展开命中保护清单时，是逐行拒绝、整行拒绝，还是要求操作员改窄前缀？
5. **IPv6 CIDR 是否同批**：若不同批，拒绝原因是否继续复用 `ipv6_environment_unsupported`？

以上任一项未定，C-F 的交付范围就只能是「上限口径核对 + 行级反馈 + 跨 Run 台账」，**不含 CIDR 展开**。

## 7. 验收标准

1. 覆盖面 Run 的 PolicyGate 拒绝未注册动作，且拒绝原因可区分"模式不允许""未授权""预算不足"。
2. 自写脚本未通过正反例闸门时，其结论只能进入可疑级，不能作为确认依据；超时、认证失败、畸形响应返回未知或失败而非"否"。
3. 缺少工具时，Run 继续执行其他资产；缺口聚合为一条并保留逐项明细；资产状态为部分覆盖。
4. 全部分支缺条件时，Run 要么等待、要么持久化受限结束并撤销自动唤醒，**不空转**。
5. 带外确认在窗口内命中与未命中分别给出"确认"与"窗口内未观察到"；回调来源 IP 与目标 IP 不一致时不误判。
6. 同一漏洞命中 N 个资产时输出一条 Finding 与 N 个入口，且每个入口可下钻到独立证据。
7. 覆盖矩阵显示已测/部分覆盖/未触达及原因；分母依据与其版本可见；分母未知时无覆盖百分比。
8. 确认级流程不出现"因等待人工确认而无法继续采证"的死锁：自动采证不等待人工，停止的是已完成采证的验证分支；**「证据要求已满足」、确认级就绪与 `confirmed` 三者分别可查询**（§3.5.1）；缺证、分类争议与失效重评各自按注明的队列目的入队且互不阻塞（§3.5.2）。
9. 非 Web TCP 服务在现有传输 profile 下完成验收样例；UDP/DNS 用例在新 profile 下验收，缺少新 profile 时明确报不支持而不是静默跳过。
10. 覆盖面模式下不存在会话、提权与第二跳动作的注册项。
11. 检查类按成熟度分级；报告按检查类分别给出命中率与覆盖率，不只给总发现数。
12. 深挖额度用尽即转向下一个资产或检查项；已确认的分支不能通过申请深挖延长；深挖不产生链条推进（提权、横向）动作。
13. 复测复用原参数、条件与环境身份并记录差异；条件不满足时报「待补证（缺条件）」而不是不成立。
14. "第一次成立、复测不成立"的产物是未决或待补证，**不产生 `refuted`**；副作用未核对的调用被拒绝作为复测基线。
15. 按 [0005 §6](./0005-capability-claim-criteria.md) 判据要求对照的主张，没有差分对照不能进入确认级；对照要求按主张类型适用，可由同一次采集中的既有观察满足，**不得为满足形式而追加目标动作**，声明的「不适用」须由复审确认并留记录与依据、**不得由模型单方豁免**（§5.1）。

## 9. 已知限制与非目标

- 覆盖面**不承诺完整覆盖**；缺口与未触达是交付的一部分，不是失败。
- 不引入外部资产测绘、SRC 归属或自动扩大目标集合。
- 不新建部署服务；PolicyGate 与工具、预算、准备同属既有 Module 的内部实现。
- 单机 Compose 的**规模化上限尚未测量**：`agentd` 顺序推进、执行账本全量序列化、事件游标行锁是三个待测热点，需要压测后决定是否调整部署结构，不能用容量算术代替实测。
- 覆盖率、成本与吞吐分别计量，不以发现数量替代。
