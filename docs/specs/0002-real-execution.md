# P1：真实执行接入、透明控制台与选择性保留

状态：待实施（初稿已评审，随 tracer 实施修订）。更新日期：2026-10-09。依据：[PROJECT.md](../../PROJECT.md)、[开发约定](../../AGENTS.md)、[ADR-0010](../adr/0010-real-execution-boundary-and-gate.md)、[当前状态](../STATUS.md)。相关决定另见 [ADR-0006](../adr/0006-windows-docker-development.md)（Windows 开发宿主）、[ADR-0007](../adr/0007-session-network-namespace.md)（每会话网络命名空间）、[ADR-0009](../adr/0009-adaptive-research-and-continuous-execution.md)（P2 持续自主执行）、[ADR-0005](../adr/0005-compose-kali-tool-retention-and-development.md)（工具保留与开发）。

本规格只描述 P1 的行为、失败分支与完成证据。它不扩大 P0 已验收的契约，也不提前实现 P2 的真实模型、联网研究与 Run 内规划。真实执行的开放由部署配置与宿主 profile 决定，不由模型、提示词或单次请求决定。

## 1. 交付目标与范围

P1 交付三件事，且三者共用现有的票据、租约、预算、证据与事件契约：

1. **执行侧真实接入**：Runner 内的受信管理组件按收窄的操作集创建、启动、限制与回收真实的 Kali 工具容器，让 `ToolCall` 第一次真实出网。
2. **透明控制台**：把真实执行的容器、网关、命令、输出、证据、资源与回收状态放进同一事件时间线，界面能区分假执行与真实执行。
3. **选择性保留**：对工具与环境版本做候选统计、手动固定与删除、回收预览，让一次性环境可清理、高频工具可保留。

P1 的全部真实执行对象是 `lab/` 自建靶场里的固定回显容器，仅使用回环与内部网络，不接触任何外部地址。真实 IP 的开放发生在 P1 验收通过之后，由操作员显式配置授权范围后另行评估。

P1 明确**不含**下列内容，它们在别处交付或永久排除：

| 不含内容 | 去处 |
| --- | --- |
| 真实模型接入、联网研究、Run 内增量规划、24×7 持续推进 | P2（ADR-0009） |
| 原生 Linux 宿主的真实隔离验收 | 另立切片（ADR-0010） |
| DNS、UDP、IPv6、loopback TCP | 需新增 profile 与对应验证（ADR-0010） |
| 动态安装（`prepare_tool`）与按需特权（`request_privilege`） | 后续阶段；P1 的真实动作全部以普通用户身份执行 |
| 自动发布到共享工具库 | 后续阶段；P1 只做候选统计与手动处置 |
| 事件保留期与“过期缺口” | P2（见 [当前状态](../STATUS.md) 与 P0 验证记录更正） |
| 多租户、账号体系、SRC 归属与资产测绘 | 永久排除（PROJECT.md §3.2） |

## 2. 用户故事

**操作员：判断这是什么执行**

1. 作为操作员，我希望在创建 Run 时就看到本次运行将使用假执行还是真实执行，以便在启动前就知道能不能拿到真实结论。
2. 作为操作员，我希望界面和响应为每一次调用标注其执行模式与执行 profile，以便不会把假数据当成真实观察。
3. 作为操作员，我希望部署不受支持或隔离就绪门槛未满足时，界面明确显示原因码而不是显示“就绪”，以便不会对着一个不会出网的平台排查工具问题。
4. 作为操作员，我希望能力状态由程序的真实条件决定而不是常量，以便状态页在 Runner 不可用时如实变红。

**操作员：处理结果未知的调用**

5. 作为操作员，我希望 Run 因未核对调用停在 `waiting`/`recovering` 时，界面告诉我停在哪一次调用、缺什么条件，以便不必从日志里自己猜。
6. 作为操作员，我希望在待核对调用上做**两值裁定**（确认未执行 / 确认已执行），以便明确区分“可以安全重派”和“只能用已有证据结算”。
7. 作为操作员，我希望裁定记录绑定我的会话、时间、依据证据与范围版本，以便事后能解释这次裁定是在什么条件下作出的。
8. 作为操作员，我希望只有“确认未执行”才允许派发一个**新的** `call_id`，以便确认已执行的动作不会因重试而重复出网。
9. 作为操作员，我希望核对只新增业务侧记录、不改写执行端账本，以便执行事实始终保持由执行层采集。
10. 作为操作员，我希望核对完成后 `resume`、`close`、`cancel` 的可用性随之变化，以便我不用记住它们被拒绝的原因。

**操作员：观察真实执行**

11. 作为操作员，我希望看到实际命令与其规范化参数 hash、cwd、执行身份、工具与环境版本，以便核对“模型说的”和“真正跑的”是否一致。
12. 作为操作员，我希望看到原始 stdout/stderr 与退出码，并直接跳到对应证据，以便判断结论是否被证据支持。
13. 作为操作员，我希望看到每个会话容器的状态、所属网关、网络模式与已放行的目标 IP/端口，以便确认出口规则与本次授权一致。
14. 作为操作员，我希望看到取消或超时之后的**进程与连接回收确认**，以便不会在残留连接仍在访问目标时以为已经停止。
15. 作为操作员，我希望在工具没有输出时仍看到心跳与运行时长，而不是虚假进度百分比，以便区分“卡住”和“慢”。
16. 作为操作员，我希望看到剩余预算、并发占用与已用调用次数，以便判断是否值得让研究继续。
17. 作为操作员，我希望事件流断线后能按游标补拉并去重，以便长时间真实执行中的观察不会因为一次掉线而缺失。
18. 作为操作员，我希望每一次策略拒绝、环境不支持、依赖失败与执行未知都以不同原因码呈现，以便恢复手段不会被混为一谈。

**操作员：证据的诚实性**

19. 作为操作员，我希望证据被截断、脱敏或未采集时界面明确标注，以便不会把不完整输出当作完整观察。
20. 作为操作员，我希望在归档失败或存储满时平台**阻断**受影响执行而不是继续确认，以便不会在证据缺失的情况下推进结论。
21. 作为操作员，我希望证据读取时重新校验 hash 与大小，并在文件缺失或哈希不符时给出明确原因，以便知道这份证据还能不能引用。
22. 作为操作员，我希望假执行与真实执行的证据在界面与导出中可分辨，以便报告不会把演示记录写成真实观察。

**操作员：能力边界**

23. 作为操作员，我希望平台明确告诉我当前 profile 只支持 IPv4/TCP，以便不会把“profile 不支持”误解为“目标没有该服务”。
24. 作为操作员，我希望覆盖记录区分“未尝试”“被执行能力边界阻断”“已尝试并获得证据”，以便覆盖陈述不被能力边界伪装成研究结论。

**人工复审者：结论边界**

25. 作为人工复审者，我希望看到哪些动作由真实执行产生、哪些来自假执行，以便只对真实证据作出裁定。
26. 作为人工复审者，我希望核对裁定与复审裁定分别保存、互不覆盖，以便机器建议、操作员核对与人工结论都能被追溯。
27. 作为人工复审者，我希望 P1 期间平台不声称已完成完整 Finding/Reviewer 报告流程，以便我不会把局部证据当成已复审结论。

**操作员：选择性保留**

28. 作为操作员，我希望看到某个工具或环境版本在多少个独立 Run 中成功使用过，以便判断它是否值得保留。
29. 作为操作员，我希望手动固定、取消固定或删除一个候选版本，以便不由程序替我决定什么值得长期保存。
30. 作为操作员，我希望在回收前看到将被删除的内容、体积与受保护项，以便在空间不足时做出选择而不是被迫接受自动删除。
31. 作为操作员，我希望活跃任务与复审的租约、以及被我固定的项不被自动回收，以便保留动作不会破坏正在运行的工作。
32. 作为操作员，我希望删除一次性环境不删除必要证据，以便结论在被保留的关键制品缺失时仍然可解释。

**部署者：门槛与回退**

33. 作为部署者，我希望默认部署继续以假执行启动且不含额外管理能力，以便升级不会静默打开真实出网。
34. 作为部署者，我希望显式启用真实执行时看到四项就绪门槛的逐项状态，以便知道缺哪一项而不是笼统的“不支持”。
35. 作为部署者，我希望可以一键回退到假执行配置而不迁移或改写业务数据，以便在真实执行出现问题时立刻回到已知状态。
36. 作为部署者，我希望真实执行所需的宿主条件与所需管理权限被记录在预检输出里，以便在新宿主上部署前就知道要准备什么。

**维护者：切片与证据**

37. 作为维护者，我希望 tracer 顺序与每条的完成证据固定下来，以便每个切片都能独立演示和验收。
38. 作为维护者，我希望真实执行端与假执行端通过同一个 Interface 契约验证，以便替换执行端不会绕过预算、策略与 outbox。
39. 作为维护者，我希望 P0 缺陷按三档分别阻塞或随切片验收，以便已知问题不会在真实执行下变成重复出网或错误归属。
40. 作为维护者，我希望新增的故障矩阵行都有对应探针，以便“未探针”不会再被写成 PASS。

## 3. 实施决定

以下为已经确定的实现决定，不是待办列表。参数、阈值与镜像版本在实施时按此处规则选取并记入验证记录。

### 3.1 受信管理组件与收窄的 Docker 操作集

真实执行仍然只由 Runner 内的受信管理组件接触容器的管理接口。该组件沿用本地隔离靶场已验证的管理模式（按标签创建与回收本轮资源、在工具进程启动前安装出口规则、按命名空间观察丢弃计数），并把可达操作收窄为一组固定动作：创建会话容器、启动与停止会话容器、创建与回收每会话网关及网络、读写本项目固定标签、查询本项目带标签的容器与进程、读取有界日志、归档证据文件。

不提供通用管理接口代理；容器镜像、挂载、网络模式、capabilities 与标签由固定 profile 决定，不接受请求中的任意值。常驻服务仍是三个。app 不获得任何容器管理能力。

### 3.2 真实动作与假动作并存

P1 引入三个真实动作：`shell.exec`、`discover_tcp_services`、`probe_http`。它们与既有假动作（`fake.collect`、`fake.verify`、`fake.review`）**并存**，由执行 profile 区分：假执行继续使用 `fake-p0-v1`，真实执行使用按版本管理的真实 profile 标识。

决定：动作标识与 profile 标识从当前写死的字面量集合改为版本化枚举，真假动作共用同一提交、查询、取消、续约与对账契约；同一 `call_id` 配不同参数 hash 一律拒绝；真实动作不做“假动作的透传包装”，各自声明参数 Schema、默认超时、输出 Schema 与可重试条件。

### 3.3 核对（Reconciliation）

`unknown` 调用的处理按 `GLOSSARY.md` 的定义实现：核对是对结果未知的调用作出的显式裁定，取值为「确认未执行」或「确认已执行」。

决定：

- 核对只新增业务侧记录，**不改写执行端账本**。
- 记录绑定操作员会话、时间、依据证据与范围版本。
- 只有「确认未执行」允许重新派发该动作，且必须使用**新的** `call_id`；原调用保留为已核对的历史。
- 「确认已执行」只用已有证据结算，不得再对同一目标发起同一动作。
- 核对完成后 Run 从 `waiting`/`recovering` 按业务事实收敛；`close` 与 `cancel` 的可用性随核对结果变化。
- 核对不改变“执行事实由执行层采集”的原则，界面不把裁定呈现为执行端结论。

### 3.4 就绪门槛与能力契约

`real_execution_ready=true` 只有在下列四项**同时**满足时才允许（ADR-0010）：

1. profile 复验覆盖票据、租约、取消、资源回收与证据归档；
2. 能力契约从写死为假值的字面量改为可表达的状态，且原因码可空；
3. 前端真正消费能力接口，并在页面标注当前执行模式与真实执行未开放的原因；
4. 默认部署保持假执行，且可一键回退。

在此之前该值保持 false，原因码保持 `environment_unsupported`。能力状态还要表达 profile 的验证状态（未验证 / 已验证 / 不支持），不再以单一字面量代替。

### 3.5 默认部署与回退

默认 Compose 部署不含任何容器管理能力，仍以假执行启动，行为与 P0 一致。真实执行由显式部署配置启用；启用后 Runner 才获得 3.1 的收窄能力。

回退即恢复默认配置：不迁移或改写业务数据，不修改已结束 Run 的历史记录，不影响活跃 Run 的既有调用对账；回退后新调用回到假执行或被明确阻断。

### 3.6 工具镜像与工具环境

工具与准备环境使用官方 `kali-rolling` 镜像的**固定 digest** 作为构建输入，发布 HuntWeave 自己的版本标签与工具清单；生产不跟随浮动标签、不在启动时做全量升级。记录解析后的包版本、构建输入与产物 digest。

一次真实执行绑定的工具/基础镜像 digest 写入 Run 清单；更新只影响后续选择，不改变活跃 Run 已选版本。

### 3.7 资源与预算

P1 沿用 `PROJECT.md` §8.4 与 §12 的现有默认值：控制租约最长 15 秒、每 5 秒续约；单次目标验证工具超时默认 60 秒、硬上限 300 秒；单次原始输出 20 MiB；单会话准备开销（下载 1 GiB、可写空间 4 GiB、单次安装/构建 10 分钟）；全局工具执行并发 4、同 IP 主动执行并发 1。

这些是保守的开发默认值，**必须在 P1 靶场实测校准**；校准结果记入验证记录，本规格不预先宣称容量或延迟指标。关键事件展示延迟与心跳目标沿用 §12.1，实际值在验收记录中给出。

### 3.8 选择性保留

P1 的选择性保留只做三件事：候选统计、手动固定/取消固定/删除、回收预览。阈值沿用 `PROJECT.md` §10.5：自动候选条件为 30 天内至少 3 个独立 Run 成功使用同一兼容工具能力，重试不累计为高频；短期缓存初始 TTL 7 天、总量 10 GiB；活跃任务与复审的租约及显式固定项优先，LRU 只回收可回收项；容量不足时显示阻断；制品回收只针对本项目管理且未被引用的对象。

自动发布到共享工具库不在 P1。由于动态安装同样不在 P1，候选机制由 P1 实际产生的工具与环境版本（预装 tool-base 版本与任务私有环境版本）驱动并验证。

### 3.9 验收宿主与验收对象

验收宿主只取本机 Windows 11 + Docker Desktop / WSL2（沿用已验证的每会话网关 profile，ADR-0006/0007）。验收对象只是 `lab/` 自建靶场中的固定回显容器，仅回环与内部网络。真实 IP 的开放留到 P1 验收通过之后。

出现 DNS、UDP、IPv6 或 loopback TCP 需求时新增 profile 与对应验证，不就地放宽现有规则。

### 3.10 触碰的 Module 与 Interface

按 `PROJECT.md` §7 的六个 Module 组织，P1 触碰其中四个：

- `execution`：新增真实执行端与受信管理组件、能力状态、目标出口与回收、工具环境键与回收预览；对外 Interface 仍是“准备环境、提交/查询/取消调用、查询能力”。
- `runs`：票据目标绑定改为实际执行目标、核对裁定的持久化与状态收敛、调度公平与预算约束；对外 Interface 仍是创建/控制 Run 与申请动作。
- `evidence`：截断、脱敏与存储满分支真实可达，归档先文件后 hash 的完整性校验保持一致。
- `timeline`：容器、网关、回收、核对与能力变化进入同一事件游标与补拉语义。

`harness` 与 `access` 在 P1 不改变职责：P1 继续使用确定性模型 Adapter，harness 仍通过同一 Interface 观察真实执行结果，不新增第二套循环。真实执行端与假执行端必须通过同一 Interface 契约验证。

## 4. 前置修复（P0 缺陷三档）

P0 验收关闭后的两轴代码审查发现三类问题。它们必须先解决，否则真实执行会把记录不准变成证据归属错误。

### ①档 必修，作为独立 Issue 先完成并阻塞首批 tracer

- **issue #9 执行票据写死目标绑定**：票据的目标 IP 与端口取自授权清单首项，而不是即将执行的真实目标；策略版本是字面量却参与 Run 级 fencing 比较。在假执行下这只是记录不准；在真实执行下它同时是**证据归属错误**与逐目标范围校验的缺失。修复后必须有多目标多端口回归：不同目标产生不同绑定的票据，越界目标被拒绝。
- **issue #10 能力就绪状态只在 API 层**：能力接口存在但前端不消费，执行就绪字段默认恒为真且从不被置否。修复后界面按真实条件标注执行模式与未就绪原因。
- **issue #11 控制台在版本冲突后静默重发操作员控制动作**：版本校验的目的正是防止操作员的决定被执行在他没看到的状态上；静默重发把防线变成自动重试。修复后冲突先展示新状态，再由操作员显式确认。
- **issue #13 单 Run 目标上限文档与实现不一致**：`PROJECT.md` §12 的保守默认值是单 Run 100 个 IP，代码却强制 5000。按产品基线收紧到 100，越界输入返回结构化原因码，并补一条按上限的边界检查。

### ②档 随对应 tracer 的验收项

- **证据分页偏移单位不一致**：一处按字节推进、另一处按字符推进，`next_offset` 的语义因此在多字节内容上不成立。随证据与真实执行切片验收，统一单位并给出跨多字节边界的检查。
- **ToolCall 状态机缺 `cancelling` 与 `denied`**：`PROJECT.md` §8.2 要求已派发的取消先进入 `cancelling`、确认进程回收后才进入 `cancelled`，未执行被拒的动作记为 `denied`。随取消与拒绝路径的验收项补齐。
- **前端原因码文案映射与后端实际发出的原因码不一致**：删除无法触达的条目、为未知条目提供兜底展示，并保证每个后端原因码在界面上都有可读表述。随透明控制台切片验收。

## 5. tracer 顺序与完成证据

每个切片都是可独立演示的纵向路径，顺序即依赖顺序。实现切片（GitHub Issue）：P1-1 [#15](https://github.com/kksty/HuntWeave/issues/15)、P1-2 拆为 [#16](https://github.com/kksty/HuntWeave/issues/16)（受信组件与容器生命周期）／[#17](https://github.com/kksty/HuntWeave/issues/17)（真实动作最小闭环）／[#18](https://github.com/kksty/HuntWeave/issues/18)（出口控制与取消回收）、P1-3 [#19](https://github.com/kksty/HuntWeave/issues/19)、P1-4 [#20](https://github.com/kksty/HuntWeave/issues/20)、P1-5 [#21](https://github.com/kksty/HuntWeave/issues/21)；前置修复为 #9–#13。

| 顺序 | 可演示成果 | 必须验证 |
| --- | --- | --- |

## 6. 测试决定

沿用并优先复用在 P0 已验证的检查缝，不新增并行测试体系：

- **纯单元检查**（不依赖容器与数据库）覆盖业务 Interface 的状态跃迁、票据校验、核对裁定的决策逻辑与原因码。
- **显式一次性数据库的集成检查**（`HUNTWEAVE_DISPOSABLE_TEST_DATABASE=1`）覆盖租约代次、条件更新、预算预留与并发领取。
- **启动探针与恢复探针**覆盖隔离与恢复的真实系统行为，包括把 P0 留下未探针的「租约到期但旧调用仍在运行」一行补成实际探针。
- **Playwright 浏览器流程**覆盖登录 → 创建 → 观察 → 控制 → 核对 → 结束操作员路径，以及能力未就绪时不得显示就绪。
- **真实执行检查只对着 `lab/` 固定回显靶场运行**，不接触任何外部地址；假执行通过不替代真实执行验收。

判定标准：测试只验证外部可观察行为（状态、事件、证据、错误码、回收确认），不为私有辅助函数逐一镜像实现。真实执行端与假执行端各自通过同一 Interface 契约检查，替换执行端不得绕过预算、策略或 outbox。

覆盖范围：`runs`（状态机、核对、调度与预算）、`execution`（票据目标绑定、租约与取消、出口规则、回收、能力状态）、`evidence`（归档完整性、截断/脱敏/存储满）、`timeline`（游标、去重、补拉）。`harness` 继续由确定性 Adapter 覆盖，不为 P1 引入第二套循环。

## 7. 不在范围

- 真实模型接入、联网研究、Run 内增量规划、24×7 持续推进 → P2（ADR-0009）。
- 原生 Linux 宿主的真实隔离验收 → 另立切片（ADR-0010）。
- DNS、UDP、IPv6、loopback TCP → 新 profile 与对应验证。
- 动态安装与按需特权 → 后续阶段；P1 真实动作全部为普通用户身份。
- 自动发布到共享工具库 → 后续阶段；P1 只做候选统计与手动处置。
- 事件保留期与过期缺口处理 → P2。
- 协议适配器与工具专用包装 → 按收益后置，不是 P1 前置条件。
- 完整 Finding/Reviewer 报告流程与人工复审的最终形态 → P2；P1 只保证证据与执行事实可被复审引用。
- 多租户、账号体系、SRC 归属与资产测绘 → 永久排除。
